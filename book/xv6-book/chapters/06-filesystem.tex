\section{磁盘布局}
\label{sec:layout}

xv6 原生文件系统的块大小是 1\,KiB，磁盘依次为：

\begin{txtcode}
[ 启动块 | superblock | 日志 | inode 块 | 空闲位图 | 数据块 ]
   0          1          2..
\end{txtcode}

superblock 记录各区的起始块号和大小，魔数为 \code{0x10203040}。几个参数与原版不同：

\begin{itemize}
  \item \code{FSSIZE}$=32768$：文件系统 32\,MiB。原来只有 1000 块，加入网络、SSH 等程序后，打包就用掉了 986 块，首次启动创建 \code{/etc} 配置时 panic “balloc: out of blocks”；
  \item \code{DIRSIZ}$=30$：文件名最长 30 字节，目录项从 16 字节变为 32 字节，为了让 TFTP 下载的 \code{kernel8-xv6\_wifi.img} 这样的长文件名能通过普通 \code{ls} 显示；
  \item inode 有 12 个直接块和 1 个一级间接块，单个文件最大 $12+256=268$ 块，即 268\,KiB。
\end{itemize}

\begin{note}
  分区再大也不会改变可分配的块数——它由 superblock 里的 \code{size} 字段决定。修改 \code{FSSIZE} 或 \code{DIRSIZ} 之后必须重新生成并整体烧录 \code{fs.img}，只替换内核会让新内核去解释旧格式的磁盘。
\end{note}

\section{块缓存、日志与 inode}

这三层基本沿用 xv6 原样，这里只说明本项目中与它们相关的两点。

\paragraph{日志.} 一次文件系统操作可能修改多个块（例如创建文件要改 inode、目录、位图）。\code{begin\_op()}/\code{end\_op()} 之间的所有修改先写进日志区，提交时一次性写回原位置；启动时 \code{fsinit()} 检查日志，把已提交但未写完的事务重做一遍。这样即使在写的过程中断电，文件系统也只会处于“操作前”或“操作后”两种状态之一。对 SD 卡来说这很重要：真机经常是直接拔电源关机的。

\paragraph{inode 睡眠锁.} inode 操作可能触发 SD 卡读写，耗时很长，不能持有自旋锁，所以每个内存 inode 有一把睡眠锁。项目中出现过一次典型的锁配对错误：在为文件描述符层加入 \code{FD\_DEVICE}、\code{FD\_VNODE}、\code{FD\_SOCKET} 等分支时，\code{fileread()} 的 \code{FD\_INODE} 分支丢了 \code{iunlock()}。

\begin{ccode}
} else if(f->type == FD_INODE){
  ilock(f->ip);
  if((r = readi(f->ip, 1, addr, f->off, n)) > 0)
    f->off += r;
  iunlock(f->ip);       // 这一行被误删
}
\end{ccode}

现象非常迷惑：启动卡在 “exec-login: inode found” 之后，调试输出显示 \code{/bin/login} 的 inode 被 PID 1 锁着，而 \code{valid=0}。原因是 \code{init} 读 \code{/etc/fstab} 时没有解锁，关闭文件后引用计数归零，这个 inode 缓存槽被 \code{iget()} 复用给了 \code{/bin/login}——槽换了主人，锁却还“记得”上一任的持有者。

\begin{note}
  \code{iput()} 不能代替 \code{iunlock()}：前者管“有多少引用”，后者管“是否正在独占访问内容”。一个有用的调试断言是：\code{iget()} 复用 \code{ref==0} 的槽时，若发现锁仍被持有，立即 panic 并打印旧的 dev/inum/owner。
\end{note}

\section{块设备：从 ramdisk 到 SD 卡}

\subsection{三个阶段}

块设备驱动经历了三次替换：

\begin{enumerate}
  \item \textbf{ramdisk}：刚移植到 \code{raspi3b} 时，用 QEMU 的 loader 把 \code{fs.img} 装到物理地址 \code{0x07000000}，\code{bread/bwrite} 直接 \code{memmove}。简单，但改动不会写回宿主机；
  \item \textbf{Arasan SDHCI}（\file{kernel/sd.c}）：BCM2837 的 EMMC 控制器，GPIO48～53 设为 ALT3。QEMU 用 \code{-drive if=sd} 把 \code{fs.img} 接到 SD 总线，数据终于可以持久保存；
  \item \textbf{SDHOST}（\file{kernel/sdhost.c}）：后来要驱动板载 Wi-Fi，而 Wi-Fi 芯片只能接在 Arasan 控制器上（GPIO34～39）。于是外置 SD 卡改由 Broadcom 自己的 SDHOST 控制器（\code{0x3f202000}）驱动，GPIO48～53 改为 ALT0。
\end{enumerate}

两种 SD 驱动对上都提供同一个接口：

\begin{ccode}
int sdsector(uint32 sector, void *buffer, int write);   // 读写一个 512 字节扇区
\end{ccode}

xv6 的块是 1\,KiB，因此一个块对应两个扇区：块 $N$ 是扇区 $2N$ 和 $2N+1$。

\subsection{SD 卡初始化}

无论哪个控制器，SD 卡协议层的初始化顺序都一样（SD 物理层规范\cite{sdspec}）：

\begin{txtcode}
400 kHz 识别时钟
CMD0                复位，卡进入 idle
CMD8                检查电压范围，确认 SD 2.0
CMD55 + ACMD41      反复发送直到卡完成上电；OCR.CCS=1 表示 SDHC（按扇区寻址）
CMD2                读 CID
CMD3                取得相对地址 RCA
CMD7                选中卡，进入 transfer 状态
(SDSC) CMD16        设置块长 512
切换到 25 MHz 工作时钟
\end{txtcode}

读一个扇区发 CMD17，写一个扇区发 CMD24，数据通过数据寄存器以轮询 PIO 方式搬运 128 个 32 位字。驱动用一把自旋锁串行化对控制器的访问。

\subsection{命令超时与恢复}

真机在 shell 里执行 \code{ls} 时偶尔 panic “fat32: read FS.IMG”。在驱动里加入事务阶段编号后得到：

\begin{txtcode}
sd: I/O failure lba=295956 write=0 phase=1 status=17f0207 irq=18000 control1=e0807
\end{txtcode}

\code{phase=1} 表示失败发生在 CMD17 的命令阶段；中断状态 \code{0x18000} 是 ERROR 加 COMMAND TIMEOUT。更麻烦的是，超时后控制器的命令/数据状态机停在 inhibit 状态，之后的每条命令都会失败。仅仅清中断位不够，还要用 \reg{CONTROL1} 的软件复位位分别复位命令线和数据线，等硬件自动清零这两位。修复后的 \code{sdsector()} 对同一扇区最多重试三次，每次失败后先 \code{recover\_io()}。这只复位主机控制器内部的状态机，卡本身仍处于 transfer 状态，不需要重新初始化。

\section{根文件系统放在哪里}
\label{sec:rootfs}

启动时 \code{rootdev\_init()} 读 SD 卡第 0 扇区，确定根文件系统的存放方式（表~\ref{tab:rootfs}），
并把发现的每个有效主分区注册到 \file{blkdev.c} 的块设备表。
此后 \code{bio.c} 通过 \code{blk\_rw()} 派发 I/O，不再直接调用 \code{rootdev\_rw()}。

\paragraph{内核命令行与 \code{root=}.} 启动分区上的 \file{cmdline.txt} 属于树莓派 VideoCore
固件：\file{start.elf} 读它，再写进设备树交给 Linux 内核。xv6 不碰这个文件，而是在旁边放自己的
\file{cmdline\_xv6.txt}（仓库根目录，\code{make install-rpi3} 负责复制）。\file{cmdline.c}
在挂上 FAT32 启动分区后读取它；文件不存在或没有启动分区（QEMU 裸镜像）时用编译期内置的
\code{CONFIG\_CMDLINE}（默认空，即自动探测）。
\code{rootdev\_init()} 用 \code{cmdline\_get("root", ...)} 查询目标分区，支持三种格式：
\code{/dev/mmcblk0p2}、\code{mmcblk0p2} 或 \code{PARTUUID=SSSSSSSS-02}（MBR 磁盘签名加分区号）。
未指定时自动探测：type 0x7f 优先，其次任何块 1 带 xv6 superblock 魔数的分区。

\paragraph{根块设备不是 FAT32 的一部分.} \file{rootdev.c} 不解释任何文件系统格式。它只读 MBR，
用 xv6 superblock 的魔数认出根分区，再把 FAT32 启动分区交给 \file{fat32.c} 挂起来，供
\code{/boot} 和固件加载使用。根分区的块里装的始终是 xv6 自己的 superblock、inode 和目录
（\ref{sec:xv6fs} 节），与 FAT32 毫无关系。块缓存的 I/O 入口 \code{blk\_rw()} 也只做地址换算，
根设备的回调 \code{root\_blk\_rw()} 不调用任何 FAT32 函数。

\section{Linux 式命名空间引导}
\label{sec:do-mounts}

内核刚启动时，块设备驱动可能还没准备好，根文件系统在哪里也可能还不知道，可 \code{/} 这个目录必须先存在。
Linux 的办法是先在内存里放一个临时的文件系统充当 \code{/}，等找到真正的根文件系统再把它换上来。
PC 发行版和嵌入式系统“找”的方式完全不同。本节先把几个名字分清楚，再比较这两种做法，最后说明
xv6 为什么、以及怎样模仿嵌入式 Linux。

\subsection{三个“根”：rootfs、根目录 / 与根文件系统}

\subsection{PC 上的 Linux：initramfs 与用户态找根}

PC 发行版（Ubuntu、Fedora 等）面对的硬件不可预测：根文件系统可能在 NVMe、SATA、USB、RAID、LVM 甚至加密盘或网络上。发行版不可能把所有驱动都编进内核，而盘符（\code{sda}、\code{sdb}）又会随插拔顺序变化，所以 bootloader 传的通常是 \code{root=UUID=…}，这里的 UUID 是 ext4、xfs 等写在\emph{文件系统超级块}里的 UUID。内核里解析 \code{root=} 的函数（\code{name\_to\_dev\_t()}，新内核中叫 \code{early\_lookup\_bdev()}）只认设备名、\code{PARTUUID=}、\code{PARTLABEL=} 和主次设备号，不会去读各种文件系统的超级块，因此找根的工作必须交给用户态：

\begin{enumerate}
  \item GRUB 把内核 \file{vmlinuz} 和一个 cpio 压缩包 \file{initrd.img}（initramfs）一起装进内存，并传入 \code{root=UUID=…}；
  \item 内核照例建立 rootfs 作为 \code{/}，再把 initramfs 解压进 rootfs。initramfs 里有一整套小型用户态：\code{/init} 脚本、busybox、\code{udevd}、\code{blkid}、内核模块；
  \item \code{kernel\_init\_freeable()} 发现 rootfs 里有 \code{/init}，就\emph{不再调用} \code{prepare\_namespace()}，直接在用户态运行这个 \code{/init}；
  \item \code{/init} 挂上 \code{/proc}、\code{/sys}，把 devtmpfs 挂到 rootfs 的 \code{/dev}，启动 \code{udevd}，用 \code{modprobe} 加载 \file{nvme.ko}、\file{ahci.ko} 等驱动，设备节点随之出现；
  \item 用 \code{blkid} 读各分区的超级块，找出 UUID 与 \code{root=} 相符的那个（必要时先 \code{cryptsetup} 解密、激活 LVM 或 RAID），把它挂到 \code{/root}（initramfs-tools）或 \code{/sysroot}（dracut）；
  \item \code{switch\_root}：把 \code{/dev}、\code{/proc}、\code{/sys}、\code{/run} 用 MS\_MOVE 搬进新根，删掉 rootfs 里的全部文件以释放内存（rootfs 本身不能卸载），然后 \code{mount --move newroot /}、\code{chroot .}，最后 \code{exec /sbin/init}（通常是 systemd）。
\end{enumerate}

\subsection{嵌入式 Linux：内核按 \code{root=} 直接挂载}

嵌入式板子的硬件是固定的：一张 SD 卡或 eMMC，驱动直接编进内核，分区布局在出厂时就定好。U-Boot 或固件在 \code{bootargs} 里传入 \code{root=/dev/mmcblk0p2 rootfstype=ext4 rootwait}，内核自己完成全部工作，不需要 initramfs：

\begin{enumerate}
  \item \code{init\_mount\_tree()} 建立 rootfs 作为 \code{/}；没有 initramfs 时，\code{default\_rootfs()} 在 rootfs 里建出 \code{/dev}、\code{/dev/console} 和 \code{/root}；
  \item \code{devtmpfs\_init()} 建立 devtmpfs，驱动注册时内核自动在里面建设备节点；
  \item rootfs 里没有 \code{/init}，于是 \code{prepare\_namespace()} 出场：\code{rootwait} 时等设备出现，再用 \code{name\_to\_dev\_t()} 把 \code{root=} 解析成设备号 \code{ROOT\_DEV}；
  \item \code{mount\_root()}：在 rootfs 里建一个设备节点 \code{/dev/root}，把它挂到 \code{/root}，然后 \code{chdir("/root")}；
  \item \code{devtmpfs\_mount()} 把 devtmpfs 挂到 \code{dev}，也就是 \code{/root/dev}（\code{CONFIG\_DEVTMPFS\_MOUNT} 打开时）；
  \item \code{mount(".", "/", MS\_MOVE)} 把根文件系统从 \code{/root} 挪到 \code{/}，盖住 rootfs；\code{chroot(".")} 让进程的根目录指向它；
  \item 运行 \code{/sbin/init}（或 \code{init=} 指定的程序）。
\end{enumerate}

\paragraph{\code{/dev/root} 是什么.} 第 3 步里的 \code{mount\_root("/dev/root", "/root")} 很容易被读成“把 \code{/dev/root} 挂到 \code{/root}”，好像挂上去的是 \code{/dev/root} 这个东西本身。其实 \code{/dev/root} 只是 rootfs 里的一个\emph{设备节点}：一个名字加一对设备号（主设备号 \code{BLOCKDEV}，次设备号是块设备表里的编号），它本身既不是文件系统，也不含数据。\code{mount\_root()} 的两个参数，一个说“到哪里找设备”，一个说“挂在哪个目录”，真正的工作由它下面三行完成：\code{node\_to\_blkdev("/dev/root")} 把名字换成设备号 1；\code{fsinit(1)} 从设备 1 读出文件系统的超级块并恢复日志；\code{fs\_mount(/root, 1)} 才把\emph{这个文件系统的根目录}盖到 rootfs 的 \code{/root} 目录上。命令行 \code{mount /dev/root /root} 也是同样的意思：挂上去的是节点所指设备上的文件系统，而不是节点。

\paragraph{xv6fs 根的 (a)--(d).} 阶段一的 (a) 把 \code{root=} 解析成分区 p2，并记下它的起始扇区 \code{root.lba}；(b) \code{register\_root()} 把块设备 1 的读写回调设为 \code{root\_blk\_rw()}，于是“设备 1 的块 $B$”就等于“卡上扇区 \code{root.lba}$+2B$”。阶段二的 (c) 建出节点 \code{/dev/root}，次设备号写 1；(d) \code{mount\_root()} 从节点读出 1，\code{fsinit(1)} 的每次 \code{bread} 经 (b) 落到 p2 上。所以设备 1 与 p2 的联系在阶段一的 (b) 就已建立，\code{/dev/root} 这个名字与设备 1 的联系在阶段二的 (c) 才建立。

\paragraph{ext2 根的 (a$'$)--(d$'$).} (a$'$) 只记下分区号 3。真正打开分区的是 ext2 驱动自己：(b$'$) \code{ext2init()} 在阶段一就把 p3 的起点记进 \code{e2.part\_lba}，此后 ext2 直接按这个起点读卡，不经过块设备表。阶段二的 (c$'$) 让 \code{/dev/root} 的次设备号指向块设备 5（\code{mmcblk0p3}），(d$'$) \code{mount\_root()} 解析这个节点，核对块设备 5 的起点与 ext2 驱动已打开的分区一致，然后登记 ext2 的 \code{super\_block} 并把它挂到 \code{/root}。从这里开始，ext2 根与 xv6fs 根走的是同一条路：\code{kchdir}、在新根的 \code{/dev} 上挂 devtmpfs、MS\_MOVE、chroot。两张调用链图的差别只剩阶段一里“分区由谁打开”和 \code{mount\_root()} 里“用哪个文件系统读它”。

注意 xv6 的“设备 1”和 Linux 的 \code{ROOT\_DEV} 不完全相同：设备 1 名叫 \code{root}，但它永远是 \emph{xv6 格式}的那个分区，供 \code{/dev/sdroot} 和 ext2 的外置日志使用；\code{/dev/root} 才对应 Linux 的 \code{ROOT\_DEV}，即“这次启动用作根文件系统的设备”——xv6fs 根时它是设备 1，ext2 根时它是设备 5。

可以把这三个阶段和图~\ref{fig:three-roots} 对上：阶段一结束时，内核只知道根文件系统在哪个分区，\code{/} 还不存在；阶段二的第 1 步让 \code{/} 指向 rootfs（图中阶段 1），第 3 步把根文件系统挂到 \code{/root}（图中阶段 2），第 4 步 MS\_MOVE 和 chroot 之后 \code{/} 指向根文件系统（图中阶段 3）。xv6fs 根和 ext2 根都完整地走这三个阶段。阶段三在这棵树上继续挂其他文件系统。

\subsection{阶段一：\code{main()} 中登记块设备、选出 ROOTDEV}
\label{sec:ns-stage1}

阶段一的主角是 \code{rootdev\_init()}（\file{rootdev.c}）。它要回答“根文件系统在哪个块设备上”，为此先要有一张块设备表。原来 \code{bio.c} 的 \code{bread}/\code{bwrite} 直接调用 \code{rootdev\_rw()}，只能访问一个设备；现在 \file{blkdev.c} 维护 \code{blk.dev[NBLKDEV]}，每项描述一个设备：

\begin{ccode}
// kernel/blkdev.h
struct blkdev {
  int      dev;      // ROOTDEV=1, BLKDEV_MMC=2, BLKDEV_MMC_PART(n)=2+n, BLKDEV_RAM(n)=7+n
  char     name[16]; // "root", "mmcblk0", "mmcblk0p2", "ram0" ...
  uint32   start;    // 分区起始扇区（整卡为 0）
  uint32   nsect;    // 分区扇区数（0 = 未知）
  uint32   bsize;    // 块大小（512 / 1024 / 4096 B）
  blk_rw_fn rw;      // I/O 回调，NULL 时用通用 mmc_rw
  void     *priv;    // 驱动私有数据（RAM 盘的页）
};
\end{ccode}

\code{rootdev\_init()} 按调用链的顺序做五件事：

\begin{enumerate}
  \item \code{blkdev\_init()} 初始化设备表，并注册主设备号 \code{BLOCKDEV}，让块设备以后能以 \code{/dev/mmcblk0p2} 这样的文件出现；
  \item 读第 0 扇区的 MBR，登记整卡 \code{mmcblk0}（dev 2）和每个主分区 \code{mmcblk0pN}（dev $2+N$）；
  \item 挂上 FAT32 启动分区，再由 \code{cmdline\_init()} 读出 \file{cmdline\_xv6.txt}（\ref{sec:rootfs} 节）；
  \item \code{check\_rootfstype()} 和 \code{root\_param\_partition()} 解析 \code{rootfstype=} 与 \code{root=}，\code{setup\_raw\_root()} 确认那个分区的第 1 块是 xv6 超级块；没有 \code{root=} 或分区不对时退回自动探测；
  \item \code{register\_root()} 把选中的分区登记为 ROOTDEV（dev 1，名字 \code{root}），它的回调 \code{root\_blk\_rw()} 负责块号到扇区的换算和 \code{/dev/sdroot} 更新时的闸门。
\end{enumerate}

从此 \code{bio.c} 的读写入口是 \code{blk\_rw(b, write)}：按 \code{b->dev} 查表，调用该设备的回调。为了容纳 ext2 的 4\,KiB 块，\code{buf.data} 从静态数组改为 \code{kalloc()} 分配的页，\code{NBUF} 从 30 扩到 64；新增的 \code{buf.error} 让非根设备的 I/O 失败只置位而不 panic，根设备失败仍 panic。

阶段一结束时，ROOTDEV 已经\emph{指向}根文件系统所在的分区，但它的超级块还没有被读过，\code{/} 也还不存在。随后 \code{ext2init()} 用 \code{rootdev\_ext2\_part()} 和 \code{rootdev\_raw\_info()} 找 ext2 分区及其外置日志，\code{vfsinit()} 初始化 netfs，\code{userinit()} 造出第一个进程，此时它的当前目录还是空的。

\begin{note}
  块设备文件（\code{/dev/mmcblk0p2} 等）经过 buffer cache，用户态只读（替换根镜像仍用 \code{/dev/sdroot}）；\code{lseek(fd, 0, SEEK\_END)} 返回分区大小。它们的节点由阶段二的 devtmpfs 建出来。
\end{note}

\subsection{阶段二：\code{forkret()} 中的 \code{prepare\_namespace()}}
\label{sec:ns-stage2}

第一个进程被调度后进入 \code{forkret()}，它在返回用户态之前调用一次 \code{prepare\_namespace()}（\file{kernel/do\_mounts.c}，文件名与 Linux 的 \file{init/do\_mounts.c} 相同）。这个函数分四步，把图~\ref{fig:three-roots} 的三个阶段依次走一遍（图~\ref{fig:prepare-namespace}）。

\paragraph{第 1 步：rootfs 成为 \code{/}.} \code{ramfs\_create()} 先用 \code{ramdisk\_create()} 分配一个 32\,KiB 的 RAM 盘并登记为块设备 ram0（dev 7），再用 \code{ramfs\_mkfs()} 直接在这块内存里写出一个空的 xv6 文件系统（超级块、inode 区、位图、只含 \code{.} 和 \code{..} 的根目录，没有日志区），最后 \code{fs\_readsuper()} 读回超级块。\code{fs\_set\_root()} 让 \code{/} 指向它的根目录，进程的当前目录也设在这里。接着像 Linux 的 \code{default\_rootfs()} 一样建出 \code{/dev}、\code{/dev/console} 和 \code{/root}。

\paragraph{第 2 步：devtmpfs.} \code{devtmpfs\_init()} 用同样的办法建出 ram1（dev 8），遍历已注册的字符设备（\code{chrdev\_name()} 给出 \code{console}、\code{input/event0} 这样的路径）和块设备表，为每个设备建一个节点。之后才注册的驱动由 \code{devtmpfs\_notify()} 交给工作队列补建。此时 devtmpfs 还没挂到任何地方。

\paragraph{第 3 步：挂上根文件系统.} 先在 rootfs 里建设备节点 \code{/dev/root}（主设备号 \code{BLOCKDEV}，次设备号 1，\ref{sec:ns-callchain} 节调用链中的 (c)；ext2 根时是 5）。\code{mount\_root()} 用 \code{node\_to\_blkdev()} 找到这个节点，从 inode 的次设备号得到设备号 1 (d)，再调用 \code{fsinit(1)}：读超级块并检查魔数，然后 \code{initlog()} 恢复日志，这一步对应 Linux 的 \code{fill\_super}。这些读操作经 \code{blk\_rw()} 进入阶段一登记的 \code{root\_blk\_rw()}，落到 p2 上。\code{fsinit()} 同时为设备 1 登记一个 \code{super\_block}（\ref{sec:vfs} 节），记下它是 xv6fs、用 \code{xv6\_iops}。最后 \code{fs\_mount()} 把设备 1 上文件系统的根目录挂到 rootfs 的 \code{/root} 上，启动日志打印：

\begin{txtcode}
VFS: Mounted root (xv6fs filesystem) on device 1 (/dev/root = mmcblk0p2).
\end{txtcode}

\code{kchdir("/root")} 之后，相对路径 \code{dev} 指的就是根文件系统里的 \code{/dev}，\code{devtmpfs\_mount("dev")} 把 devtmpfs 挂上去。新做的 \file{fs.img} 里还没有 \code{/dev} 目录（以前由 \code{init} 创建），这里发现缺失会先建出这个挂载点。

\paragraph{第 4 步：MS\_MOVE 与 chroot.} \code{fs\_move\_mount()} 把“挂在 \code{/root}”的根文件系统改为“挂在 rootfs 的根目录上”，挂在它下面的 devtmpfs 随之从 \code{/root/dev} 变成 \code{/dev}；\code{fs\_set\_root()} 再把 \code{/} 改指根文件系统的根目录。rootfs 从此被压在下面，只剩 \code{/dev/root} 这个名字还留在它里面。

\code{prepare\_namespace()} 返回后，\code{forkret()} 运行 \code{blkdev\_selftest()}（读 \code{mmcblk0} 扇区 0 两次，确认第二次命中缓存），然后经 \code{usertrapret()} 回到用户态，执行 initcode。

\subsection{支撑这四步的机制：超级块、日志、挂载表与 \code{namex()}}
\label{sec:ns-mech}

上面四步调用的 \code{fs\_readsuper()}、\code{fs\_mount()}、\code{fs\_move\_mount()}、\code{fs\_set\_root()} 都在 \file{fs.c}。原来的 xv6 只有一个根文件系统，所以既不需要挂载表，路径解析也直接从常量 \code{iget(ROOTDEV, ROOTINO)} 开始；现在同一时刻有三个文件系统（rootfs、devtmpfs、根文件系统，都用 xv6fs 磁盘格式），这几处都要改。

\paragraph{每个设备一份超级块（第 1、2、3 步）.} 全局的 \code{struct superblock sb} 改为 \code{sbs[NBLKDEV]}，\code{balloc}、\code{ialloc} 等通过 \code{getsb(dev)} 取得对应设备的 xv6 磁盘超级块。\code{fs\_readsuper(dev)} 读块 1、检查魔数并存入 \code{sbs[dev]}，同时在 VFS 的 \code{supers[]} 里登记一个内存中的 \code{super\_block}（类型、函数表、根 inode 号，\ref{sec:vfs} 节）；\code{fsinit(dev)} 在它之后再做日志恢复。前者是 xv6fs 自己的磁盘格式，后者是所有文件系统共用的“实例描述”，相当于 Linux 里 \code{struct ext2\_sb\_info} 与 \code{struct super\_block} 的关系。

\paragraph{只有根文件系统有日志（第 1、2 步先于第 3 步）.} 第 1、2 步在 rootfs 和 devtmpfs 里建目录和节点时，根文件系统的日志还没初始化（那是第 3 步的事）。因此日志锁改由 \code{iinit()} 里的 \code{loginit()} 提前建立，\code{log\_write()} 遇到不属于日志设备的块（\code{log.size==0 || b->dev!=log.dev}）就直接 \code{bwrite()} 写穿。RAM 盘的内容重启即消失，不需要崩溃一致性。

\paragraph{挂载表与路径穿越（第 3、4 步）.} \file{fs.c} 新增一张挂载表，每项记录“目录 \code{mp} 被设备 \code{dev} 的根目录覆盖”。这是系统里\emph{唯一}的挂载表：rootfs 上的根文件系统、devtmpfs，以及阶段三挂上的 procfs、FAT32、ext2 都是其中的一项：

\begin{ccode}
// kernel/fs.c
struct fsmount {
  int          used;
  struct inode *mp;           // 被覆盖的目录（持引用）
  uint         dev;           // 挂载上来的文件系统设备号
  char         fstype[12], source[24];
  char         path[MAXPATH]; // 显示路径（用于 /proc/mounts）
};
\end{ccode}

\code{namex()} 在两处查这张表：

\begin{ccode}
// 向下：lookup 到被覆盖的目录 -> 替换为被挂载文件系统的根目录
ip = follow_mount(next);

// 向上：".." 从被挂载文件系统的根目录出发 -> 先退回挂载点目录
if(namecmp(name, "..") == 0)
    ip = follow_dotdot(ip);
\end{ccode}

第 3 步的 \code{fs\_mount()} 往表里加一项，于是解析 \code{/root/...} 时，\code{follow\_mount()} 会在 \code{root} 这一级从 rootfs 跳进 ROOTDEV。“是不是某个文件系统的根目录”由 \code{isfsroot()} 判断：比较的是该设备 \code{super\_block} 里的 \code{rootino}（xv6fs 为 1，ext2 为 2），所以同样的跳转对 ext2 也成立。同一个文件系统不能挂两次，\code{fs\_mount()} 发现设备已在表里就拒绝。第 4 步的 \code{fs\_move\_mount()} 只是把这一项的 \code{mp} 从 rootfs 的 \code{/root} 改成 rootfs 的根目录，并把所有子挂载的显示路径一并改写（\code{/root/dev} $\to$ \code{/dev}）。

\paragraph{\code{/} 从哪里开始（第 1、4 步）.} \code{namex()} 解析绝对路径时调用 \code{rootdir()}，它返回 \code{fs\_root}——第 1 步设为 rootfs 的根目录，第 4 步由 \code{fs\_set\_root()} 改为根文件系统的根目录。以切换后的两个路径为例：

\begin{txtcode}
namei("/bin/sh")    rootdir() = (dev 1, inode 1)  -> bin -> sh        根文件系统
namei("/dev/tty")   rootdir() = (dev 1, inode 1)  -> dev
                    follow_mount: dev 被覆盖 -> (dev 8, inode 1) -> tty  devtmpfs
\end{txtcode}

\code{follow\_dotdot()} 遇到 \code{fs\_root} 时原地不动，所以 \code{/..} 仍是 \code{/}，进程无法退回被压住的 rootfs。另外，\code{fs\_create()} 是 \code{kmknod()} 和系统调用共用的入口，它检查文件系统是否可写，再调用目录所在文件系统的 \code{iop->create}；\code{sys\_unlink()}、\code{sys\_rename()} 用 \code{fs\_is\_mountpoint()} 拒绝删除或移走挂载点。

\subsection{阶段二的另一条分支：ext2 作为根文件系统}
\label{sec:ext2-root}

\code{rootfstype=} 可以是 \code{xv6fs}（默认）或 \code{ext2}，写成别的值只引出一行警告，仍按 xv6fs 启动。把 \file{cmdline\_xv6.txt} 写成 \code{root=/dev/mmcblk0p3 rootfstype=ext2}，p3 上的 ext2（第~\ref{chap:optional} 章）就成为 \code{/}。有了统一的 VFS（\ref{sec:vfs} 节），ext2 根和 xv6fs 根只在两个地方不同：

\begin{enumerate}
  \item 阶段一，\code{rootdev\_init()} 记下 ext2 根所在的分区（\code{rootdev\_ext2\_part()}），但仍然寻找 xv6 分区并登记设备 1：\code{/dev/sdroot} 和 ext2 的外置日志都在那里；找不到也不 panic。随后 \code{ext2init()} 优先尝试这个分区，并记下它的起始扇区；
  \item 阶段二，\code{prepare\_namespace()} 让 \code{/dev/root} 指向 \code{mmcblk0p3}（设备 5），\code{mount\_root()} 按 \code{rootdev\_fstype()} 选择 ext2：核对分区后调用 \code{ext2\_register\_super(5)}，而不是 \code{fsinit()}。
\end{enumerate}

其余步骤完全相同：ext2 先挂到 rootfs 的 \code{/root}，\code{kchdir("/root")}，在 ext2 自己的 \code{/dev} 上挂 devtmpfs（目录不存在时内核经 \code{e2\_create()} 建出它），再 MS\_MOVE 和 chroot。

\begin{note}
  早先的实现不是这样。那时 ext2 只能挂在 \file{vfs.c} 的“路径前缀挂载表”里，它的目录不是 xv6 inode，既进不了 \file{fs.c} 的挂载表，也不能成为 MS\_MOVE 和 chroot 的对象，只好用 \code{mount\_ext2\_root()} 直接挂到 \code{/}，devtmpfs 则挂在被遮住的 rootfs 的 \code{/dev} 上，再靠 \code{fs\_native\_covers()} 让 \code{/dev} 开头的路径绕过 ext2。两张挂载表、两套路径解析，正是把 VFS 改成 Linux 那样“每个文件系统一张函数表、一张挂载表”的直接原因；改完以后这些特殊处理全部删掉了。
\end{note}

\code{exec} 和当前目录本来就按 inode 工作（\ref{sec:vfs-cwd} 节），\code{init}、\code{sh}、\code{login} 不用改。启动日志：

\begin{txtcode}
Kernel command line: root=/dev/mmcblk0p3 rootfstype=ext2
rootdev: root=/dev/mmcblk0p3 rootfstype=ext2 -> mmcblk0p3
ext2: p3 ready rw start=1884160 sectors=248463360 block=4096 groups=948
VFS: Mounted root (ext2 filesystem) on device 5 (/dev/root = mmcblk0p3).
devtmpfs: mounted
VFS: root moved over rootfs, chroot done; running /init
\end{txtcode}

ext2 分区里要有 \code{/init} 和 \code{/bin} 下的程序。\code{make install-rpi3-ext2root RPI3\_EXT2\_DEV=/dev/rdisk4s3} 用 e2fsprogs 的 \code{debugfs} 把它们写进去，不重新格式化，分区上原有的文件（如 \code{video/}）不受影响；\code{/etc} 下的配置由 \code{init} 第一次启动时创建。

限制：ext2 驱动没有实现设备节点和硬链接（\code{ext2\_iops} 里没有 \code{link}，\code{create} 拒绝 \code{T\_DEVICE}），所以 \code{mknod} 只在 devtmpfs 的 \code{/dev} 里有效；\file{/etc/fstab} 里“ext2 挂到 \code{/mnt/ext2}”那一行会失败，因为同一个文件系统已经挂在 \code{/}，挂载表不允许挂两次，启动时会看到一行 \code{vfs: cannot mount ext2 at /mnt/ext2}，不影响使用。回到 xv6fs 根文件系统只需把 \file{cmdline\_xv6.txt} 改回 \code{rootfstype=xv6fs}（或删掉它）。

\subsection{阶段三：\code{/init} 与用户态看到的结果}
\label{sec:ns-stage3}

initcode 执行 \code{exec("/init")}。这时 \code{namex()} 从 \code{fs\_root} 出发，用根文件系统自己的 \code{lookup}（xv6fs 是 \code{xv6\_lookup()}，ext2 是 \code{e2\_lookup()}）找到 \code{/init}。\code{/init} 先打开 \code{/dev/ttyS0}：devtmpfs 已经提供了节点，它不再 \code{mknod}，只有在打不开时（旧内核、没有 devtmpfs）才退回在根文件系统上建静态节点。然后 \code{mount\_fstab()} 读 \file{/etc/fstab}，经 \code{sys\_mount()} $\to$ \code{vfsmount()} 为 procfs、FAT32 和 ext2 登记 \code{super\_block}，再用 \code{fs\_mount()} 挂进同一张挂载表。

挂载表的内容可以从 procfs 看到：\code{/proc/mounts} 就是 \code{fs\_mounts\_format()} 的输出，\code{ro}/\code{rw} 取自各自的 \code{super\_block}；\code{/proc/cmdline} 是 \code{cmdline\_get\_all()} 的内容：

\begin{txtcode}
$ cat /proc/cmdline
root=/dev/mmcblk0p2 rootfstype=xv6fs
$ cat /proc/mounts
/dev/root / xv6fs rw 0 0
devtmpfs /dev devtmpfs rw 0 0
proc /proc procfs ro 0 0
bootfs /boot fat32 rw 0 0
ext2 /mnt/ext2 ext2 rw 0 0
\end{txtcode}

rootfs（ram0）被根文件系统盖住以后不再列出，和新版 Linux 一致；\code{/dev/root} 这个名字只存在于 rootfs 里，正是 Linux 的习惯。ext2 分支下，第一行是 \code{/dev/root / ext2 rw 0 0}，第二行同样是 \code{devtmpfs /dev}，只是少了 \code{/mnt/ext2} 那一行。

\subsection{用 fs-trace 看三个文件系统}
\label{sec:fs-trace}

前面几节讲的是代码怎么走，这一节换个角度：打开 \file{kernel/fs\_trace.h} 里的跟踪开关，启动一次，把内核打印的 \code{fs-trace:} 日志整理出来，看看启动结束时三个文件系统在“磁盘”上到底是什么样子。日志里有这几类记录：

\begin{itemize}
  \item \code{fill\_super}：读块 1 得到的磁盘 superblock 各字段；\code{register\_super}：登记到 VFS 的 \code{super\_block}；
  \item \code{iget\_path}/\code{xv6\_read\_inode}：inode 缓存是否命中，以及 dinode 在哪个磁盘块的第几个位置；
  \item \code{bmap}：文件块号经 \code{addrs[]} 换成磁盘块号；
  \item \code{dirlookup}：逐项读出的目录项（偏移、名字、inode 号），以及命中或未命中。
\end{itemize}

这次启动用的是 xv6fs 根（\code{root=/dev/mmcblk0p2}），日志共 4408 行。下面只看三个文件系统：rootfs（dev 7）、devtmpfs（dev 8）和根文件系统（dev 1）。它们是三个不同的文件系统：rootfs 和 devtmpfs 是内核在启动时用 \code{ramfs\_mkfs()} 在内存盘 ram0、ram1 上现做出来的，内容随启动生成、重启即消失，各有自己的用途；根文件系统是 \code{mkfs} 预先做好、烧在 SD 卡 p2 上的 \file{fs.img}。三者只是借用了同一种磁盘格式（xv6fs）和同一张函数表 \code{xv6\_iops}，所以日志里的 \code{type} 都是 \code{xv6fs}，superblock 的字段也一样。表~\ref{tab:fstrace-sb} 是三者的 superblock。

\paragraph{读图~\ref{fig:fstrace-dev7}：inode 号、槽号与目录项偏移.} 图里有三种编号，初读容易混在一起。

\emph{inode 号}是 inode 的编号。\code{fs.h} 定义 \code{ROOTINO} 为 1：编号 0 不用，因为目录项里 \code{inum==0} 表示空槽，所以根目录取第一个可用号 1。\code{ramfs\_mkfs()} 把根写在 ino 1，之后 \code{ialloc()} 从 1 往上找第一个空闲 dinode，编号就按创建顺序发出：\code{/dev} 是 2，\code{/dev/console} 是 3，\code{/root} 是 4，第 3 步的 \code{/dev/root} 是 5。ext2 的约定不同，inode 1 留给坏块表，根是 2；所以 VFS 判断“是不是根目录”时比较的是各自 \code{super\_block} 的 \code{rootino}，而不是写死的 1。

\emph{槽号}（图左的 \code{\#N}）是 dinode 在 inode 块里的位置，完全由 inode 号算出，dinode 自己并不存编号：
\[
  \text{块号} = \code{inodestart} + \lfloor \text{ino}/16 \rfloor,\qquad
  \text{槽号} = \text{ino} \bmod 16,\qquad
  \text{块内字节} = \text{槽号}\times 64 .
\]
rootfs 只有 16 个 inode，全在块 2，所以 \code{\#N} 恰好等于 ino $N$；\code{\#0} 对应 ino 0，不用。inode 区从哪一块开始看 \code{inodestart}：rootfs、devtmpfs 是块 2（前面只有 boot 和 superblock），SD 卡上的根文件系统是块 32（块 2--31 是日志），那里 ino 1 就在块 32 的第 1 个槽。

\emph{目录项偏移}（图右的 \code{off N}）是目录项在目录数据块里的位置，每项 32 字节，按写入顺序排。每个目录创建时先写 \code{.}（指自己）和 \code{..}（指父目录），所以 \code{/dev} 的块 6 第一项 \code{.} 指向 ino 2，第二项 \code{..} 指向 ino 1；根目录没有父目录，它的 \code{..} 指回自己。目录项和槽号靠目录项里写的 inode 号连起来，两者顺序并不一致：块 6 的 off 32 对应 \code{\#1}，off 96 对应 \code{\#5}。

还要注意图里有两个都叫 \code{root} 的目录项：块 5（\code{/} 的内容）off 96 的 \code{root} 是目录 \code{/root}（ino 4，挂根文件系统用的挂载点），块 6（\code{/dev} 的内容）off 96 的 \code{root} 是设备节点 \code{/dev/root}（ino 5）。inode 只用 \code{addrs[]} 指向数据块，指向 inode 的只有目录项，所以从 ino 1 到 ino 5 要走两层，这正是日志第 2127 行查找 \code{/dev/root} 的过程：
\begin{center}
  ino 1 $\to$ \code{addrs[0]} $\to$ 块 5 $\to$ \code{dev} $\to$ ino 2 $\to$ \code{addrs[0]} $\to$ 块 6 $\to$ \code{root} $\to$ ino 5
\end{center}

\paragraph{dinode 的 64 字节.} “inode 1”同时指三样东西：编号 1；磁盘块 2 第 1 个槽里的 64 字节 \code{struct dinode}；\code{ilock} 之后 \code{itable[]} 里的内存副本 \code{struct inode}（多了 \code{dev}、\code{ref}、锁和 \code{iop}）。\code{iget(7, 1)} 只在 \code{itable} 里记下 dev 7、ino 1，置 \code{valid=0}，并不读盘；\code{ilock} 发现 \code{valid==0} 才调用 \code{xv6\_read\_inode()}，按上面的公式读块 2、取出偏移 64 处的 dinode：

\begin{ccode}
struct dinode {            // kernel/fs.h
  short type;              // 2 B
  short major;             // 2 B
  short minor;             // 2 B
  short nlink;             // 2 B
  uint  size;              // 4 B
  uint  addrs[NDIRECT+1];  // 13 x 4 = 52 B：addrs[0..11] 直接块，addrs[12] 一级间接块
};                         // 共 64 B，IPB = 1024 / 64 = 16
\end{ccode}

rootfs 的 ino 1 在启动结束时（4 个目录项，\code{size}=128）逐字段如表~\ref{tab:fstrace-dinode}。\code{nlink} 是 3：\code{ramfs\_mkfs()} 做好时为 1（日志第 23 行的 dump 是在建 \code{/dev} 之前打印的，那时 \code{size} 还是 64、\code{nlink} 还是 1），之后 \code{xv6\_create()} 每建一个子目录就给父目录 \code{nlink++}，因为子目录的 \code{..} 也指向它；建了 \code{/dev}、\code{/root} 两个子目录，就是 $1+2=3$。根目录由两部分组成：ino 1 这 64 字节是关于它的信息，块 5 的 1024 字节是它的内容（目录项表），两者靠 \code{addrs[0]=5} 连起来；图~\ref{fig:fstrace-dev7} 右边写“块 5 · 目录 /”，意思是“ino 1 的 \code{addrs[0]} 指向的内容块”。

\subsection{回到用户态：\code{trapret} 中的中断竞争}

阶段二的最后一步是 \code{forkret()} 调用 \code{usertrapret()}，经 \code{trapret} 返回用户态。不只是第一个进程，每个新 fork 出的子进程第一次运行都走这条路，而这里藏着一个早就存在的竞争，引入块设备层后时序变化才在 QEMU 上暴露出来。

\code{trapret} 先用 \code{urestorereg} 装载 \reg{ELR\_EL1}/\reg{SPSR\_EL1}，再 \code{eret}。\code{forkret()} 开头的 \code{release(\&p->lock)} 会经 \code{pop\_off()} 按调度器当时的状态重新开中断，于是 \code{trapret} 是在开中断的情况下运行的。IRQ 若恰好落在 \code{msr} 与 \code{eret} 之间，就会把这两个寄存器改写成它自己的 EL1 返回现场，\code{eret} 回到的是 EL1 的 \code{trapret+0x14}，此时 \code{sp} 已等于内核栈顶，下一条 \code{ldp} 读到栈上方未映射的保护页。跑 \code{usertests forkfork}/\code{concreate} 时看到的正是 \code{elr=trapret+0x14}，\code{far} 正好是内核栈顶。修复是在 \code{urestorereg} 前无条件屏蔽中断：

\begin{asmcode}
trapret:
    msr daifset, #0xf    // 屏蔽：ELR/SPSR 加载到 eret 之间不能有 EL1 IRQ
    urestorereg
    eret
\end{asmcode}

\begin{note}
  \code{daifset} 只影响 EL1 当前的 PSTATE；\code{eret} 会从 \reg{SPSR\_EL1} 恢复 DAIF，回到用户态后的中断状态由 SPSR 决定，不受这条指令影响。
\end{note}

\subsection{从路径前缀表到统一 VFS}

最初的 ext2 驱动只能通过两个专用系统调用 \code{ext2read}、\code{ext2readdir} 访问，普通的 \code{ls}、\code{cat} 完全不知道它的存在。第一版 VFS 的办法是在 xv6 原有的路径解析\emph{外面}再包一层：\file{vfs.c} 维护一张“路径前缀挂载表”，\code{sys\_open()} 先用 \code{findmount()} 做最长前缀匹配，命中 \code{/boot}、\code{/mnt/ext2} 这样的挂载点就把相对路径交给后端的 \code{vnode\_ops}（参数都是路径），打开结果是一种新的描述符 \code{FD\_VNODE}；不命中才走原生的 \code{namei()}。

这个方案让 \code{ls}、\code{cat}、\code{mv} 很快就能访问其他文件系统，但系统里从此有两套东西并存：两张挂载表（\file{vfs.c} 的路径前缀表和 \file{fs.c} 的 inode 层挂载表）、两种打开的文件（\code{FD\_INODE} 与 \code{FD\_VNODE}）、两条路径解析（\code{findmount()} 与 \code{namex()}）。\code{open}、\code{mkdir}、\code{chdir}、\code{exec} 每个系统调用都要先问一句“这个路径归谁”。到了要把 ext2 当根文件系统时问题就暴露出来了：ext2 的目录不是 xv6 inode，进不了 inode 层挂载表，也就不能 MS\_MOVE、不能 chroot（\ref{sec:ext2-root} 节）。

Linux 的做法是反过来：\emph{所有}文件系统，包括“原生”的那个，都通过同一组函数表接入；路径解析只有一条，每走一级就调用当前目录所在文件系统的 \code{lookup}；挂载表也只有一张。本项目最终也改成了这种结构。对照如下：

    \code{struct fsmount}（\code{mtab}） & “目录 X 被文件系统 Y 的根盖住” & \code{struct mount} \\
    \code{namex()} + \code{iop->lookup} & 逐级解析路径 & \code{link\_path\_walk()} + \code{->lookup} \\
    \code{pathfs\_iops} & 按路径工作的小文件系统的通用实现 & \code{simple\_*}、\code{libfs} \\
    \bottomrule
  \end{tabularx}
\end{table}

xv6 没有 dentry 缓存：目录项不单独缓存，\code{lookup} 每次都到文件系统里查；也没有把 \code{file\_operations} 单独分出来，读写操作和目录操作放在同一张表里。

\subsection{\code{super\_block} 与 \code{inode\_ops}}

\file{kernel/vfs.h} 定义了两个结构。\code{super\_block} 按设备号索引，一个设备号就是一个文件系统实例：

\begin{ccode}
// kernel/vfs.h
struct super_block {
  int    used;
  int    dev;          // 设备号，即这个实例的编号
  char   type[12];     // "xv6fs" "ext2" "fat32" "procfs" "netfs"
  struct inode_ops *iop;
  uint   rootino;      // 根目录的 inode 号：xv6fs 1，ext2 2，按路径的为 hash("/")
  int    readonly;
  int    logged;       // 写操作要分批走 xv6 日志（只有 xv6fs）
  int    pathbased;    // 对象以路径命名（FAT32、procfs、netfs）
  void   *priv;        // 文件系统私有数据
};
\end{ccode}

块设备上的文件系统用块设备号（xv6fs 根 1、rootfs 7、devtmpfs 8、ext2 分区 3～6 之一），没有块设备的文件系统用 \code{vfs.h} 里的伪设备号（\code{PROCFS\_DEV} 20、\code{FATFS\_DEV} 21、\code{NETFS\_DEV} 22）。登记由各文件系统自己完成：\code{fs\_readsuper()} 登记 xv6fs，\code{ext2\_register\_super()} 登记 ext2，\code{vfsmount()} 登记按路径的文件系统。

\code{inode\_ops} 是每种文件系统的函数表，\code{struct inode} 增加一个 \code{iop} 指针指向它：

\begin{ccode}
struct inode_ops {
  int  (*read_inode)(struct inode*);             // ilock() 第一次加锁时填充 inode
  void (*evict)(struct inode*);                  // iput() 放掉最后一个引用时
  struct inode *(*lookup)(struct inode *dp, char *name);   // dp 已加锁
  struct inode *(*create)(struct inode *dp, char *name,
                          short type, short major, short minor);
  int  (*unlink)(struct inode *dp, char *name);
  int  (*link)(struct inode *dp, char *name, struct inode *ip);
  int  (*rename)(struct inode *odp, char *oname, struct inode *ndp, char *nname);
  int  (*read)(struct inode*, int user_dst, uint64 dst, uint64 off, uint n);
  int  (*write)(struct inode*, int user_src, uint64 src, uint64 off, uint n);
  int  (*truncate)(struct inode*, uint64 size);
  int  (*open)(struct inode*, int omode);        // 可选：打开时的文件系统检查
  int  (*fsync)(struct inode*);
};

struct inode {                   // kernel/file.h
  uint dev, inum;  int ref;
  struct inode_ops *iop;         // 所属文件系统的函数表
  char path[MAXPATH];            // 只用于按路径的文件系统
  struct sleeplock lock;  int valid;
  short type, major, minor, nlink;  uint64 size;
  uint addrs[NDIRECT+1];         // xv6fs 的块地址
  uint32 fsdata[4];              // 其他文件系统的私有数据
};
\end{ccode}

\code{size} 扩成 64 位，因为 ext2 和 FAT32 上的文件可以超过 4\,GiB；文件名分量的上限 \code{NAMEMAX} 是 128，xv6fs 自己仍只存 14 个字符。

xv6 的 inode 缓存原样保留，只在三个地方挂上钩子：

\begin{itemize}
  \item \code{iget(dev, inum)} 在 \code{itable} 里找或分配一项，并设 \code{ip->iop = getsuper(dev)->iop}；
  \item \code{ilock()} 发现 \code{valid==0} 时调用 \code{iop->read\_inode()}，原来那段读 \code{dinode} 的代码成了 \code{xv6\_read\_inode()}；
  \item \code{iput()} 放掉最后一个引用时调用 \code{iop->evict()}，原来“链接数为 0 就截断并释放”的代码成了 \code{xv6\_evict()}。
\end{itemize}

\subsection{一次跨文件系统的路径解析}

\code{namex()} 只改了一行：原来调用 \code{dirlookup()}，现在调用 \code{ip->iop->lookup(ip, name)}。挂载点的穿越仍由 \ref{sec:ns-mech} 节的 \code{follow\_mount()}/\code{follow\_dotdot()} 完成，判断“是不是文件系统的根”改用 \code{isfsroot()}：比较 \code{ip->inum} 与该设备 \code{super\_block} 的 \code{rootino}。以 xv6fs 根上的 \code{/mnt/ext2/d/a.txt} 和 \code{/proc/1/status} 为例（inode 号仅作示意）：

\begin{txtcode}
namei("/mnt/ext2/d/a.txt")
  rootdir()             (dev 1, ino 1)      xv6fs 根
  xv6_lookup("mnt")     (dev 1, ino 25)
  xv6_lookup("ext2")    (dev 1, ino 26)     follow_mount: 被设备 5 盖住
                     -> (dev 5, ino 2)      fs_dev_root(5)：ext2 的根，rootino = 2
  e2_lookup("d")        (dev 5, ino 12)     查 ext2 的目录块
  e2_lookup("a.txt")    (dev 5, ino 13)
namei("/proc/1/status")
  xv6_lookup("proc")    (dev 1, ino 27)     follow_mount: 被设备 20 盖住
                     -> (dev 20, hash("/"))           procfs 的根
  pfs_lookup("1")       (dev 20, hash("/1"))          path = "/1"
  pfs_lookup("status")  (dev 20, hash("/1/status"))   path = "/1/status"
\end{txtcode}

反方向的 \code{..} 也一样：在 \code{(dev 5, ino 2)} 上遇到 \code{..}，\code{isfsroot()} 为真，\code{follow\_dotdot()} 先退回挂载点 \code{(dev 1, ino 26)}，再由 xv6fs 查它的 \code{..}。

\subsection{文件描述符与系统调用}

打开任何文件系统上的普通文件，得到的都是 \code{FD\_INODE}；\code{FD\_VNODE} 和 \code{vnode} 一起删掉了。各系统调用只做与文件系统无关的事，具体工作交给函数表：

\begin{itemize}
  \item \code{fileread()}、\code{filepread()} 调用 \code{iop->read}；\code{exec()} 读 ELF 也一样，\code{struct execsrc} 只剩一个 inode 指针；
  \item 写操作由 \code{inode\_write()} 统一处理：xv6fs（\code{sb->logged}）照原来的办法每次只写几块、每批一个日志事务，其他文件系统有自己的一致性机制，整段交给 \code{iop->write}；
  \item \code{sys\_open()} 对普通文件依次检查：要写而文件系统只读则失败；有 \code{O\_TRUNC} 就调用 \code{iop->truncate(ip, 0)}；最后调用可选的 \code{iop->open}，FAT32 在这里取得写句柄；
  \item 目录读取：xv6fs 的目录本来就是 \code{struct dirent} 数组。其他文件系统通过 \code{vfs\_dir\_read()} 把自己的目录项“翻译”成 xv6 的 dirent 流，每 16 字节偏移一项，\code{ls} 不用改。名字超过 14 字符时截断显示，\code{open} 时仍可用全名；
  \item \code{fs\_create()}、\code{fs\_unlink()}、\code{fs\_link()}、\code{fs\_rename()} 先检查文件系统是否可写、是否提供该操作；\code{link}、\code{rename} 还要求两端在同一设备上，跨文件系统一律拒绝（与 Linux 的 \code{EXDEV} 相同）；\code{unlink}、\code{rename} 遇到挂载点返回失败（\code{EBUSY}）。
\end{itemize}

顺带补上了 xv6fs 自己的 \code{rename}：\code{xv6\_rename()} 在同一个日志事务里先加新名字、再清掉旧目录项，目前只支持普通文件，目标已存在时拒绝。

\subsection{当前目录与 \code{exec}}
\label{sec:vfs-cwd}

第一版 VFS 里，最长前缀匹配只认绝对路径，而原生 xv6 的当前目录是一个 inode 指针 \code{p->cwd}，两者合在一起有两个明显的漏洞：\code{cd /mnt/ext2} 只会进入原生根文件系统里那个被挂载点遮住的空目录；\code{exec()} 只调用 \code{namei()} 和 \code{readi()}，挂载点上的程序根本无法运行。

当时的修复是让路径在进入系统调用时就变成绝对路径。\code{struct proc} 增加一个字段 \code{cwdpath}，记录当前目录的规范化绝对路径（\code{fork}、\code{clone} 复制它，\code{prepare\_namespace()} 在 chroot 之后置为 \code{/}）。\file{sysfile.c} 的 \code{abspath()} 把相对路径接在 \code{cwdpath} 后面，再逐段处理 \code{.} 和 \code{..}：

\begin{txtcode}
cwdpath = /mnt/ext2/d      输入 ../a.txt     ->  /mnt/ext2/a.txt
cwdpath = /bin             输入 ../etc       ->  /etc
cwdpath = /                输入 mnt/ext2/d/e ->  /mnt/ext2/d/e
\end{txtcode}

xv6 没有符号链接，所以按文字处理 \code{..} 与沿目录树向上走的结果完全相同。统一 VFS 之后这层处理仍然保留：\code{open}、\code{mkdir}、\code{unlink}、\code{rename}、\code{link}、\code{mknod}、\code{mount}、\code{chdir}、\code{exec} 一进来就调用 \code{abspath()}。不同的是，现在所有文件系统上的目录都有 inode，\code{chdir()} 只剩一条路：\code{namei()} 找到目录、检查类型、换掉 \code{p->cwd}、更新 \code{cwdpath}，不再需要“目录只以路径存在”的特殊情况。

\code{exec()} 读 ELF 的来源也只剩一种：

\begin{ccode}
struct execsrc {                 // kernel/exec.c
  struct inode *ip;              // 任何文件系统上已加锁的 inode
};

static int srcread(struct execsrc *src, uint64 dst, uint off, uint n) {
  return src->ip->iop->read(src->ip, 0, dst, off, n);   // xv6_read / e2_read / pfs_read
}
\end{ccode}

\code{begin\_op()} $\to$ \code{namei()} $\to$ \code{ilock()} 之后检查是普通文件，读 ELF 头、程序头和 \code{loadseg()} 都调用 \code{srcread()}。这样 \code{/mnt/ext2} 和 \code{/boot} 上的程序都能直接运行，ext2 当根文件系统时 \code{/init} 也是这样被加载的：

\begin{shcode}
$ cd /mnt/ext2/d
$ cat /bin/echo > e
$ ./e hi from ext2
hi from ext2
$ cd /
$ mnt/ext2/d/e relative exec
relative exec
\end{shcode}

\subsection{三类实现}

\paragraph{xv6fs（\code{xv6\_iops}）.} 原来 \file{fs.c} 和 \file{sysfile.c} 里的代码几乎原样搬进函数表：\code{xv6\_lookup()} 就是 \code{dirlookup()}，\code{xv6\_create()} 是原来 \code{create()} 的主体，\code{xv6\_unlink()}、\code{xv6\_link()} 是原来 \code{sys\_unlink()}、\code{sys\_link()} 的中段，\code{xv6\_read()}/\code{xv6\_write()} 就是 \code{readi()}/\code{writei()}（多一个 4\,GiB 的边界检查），\code{xv6\_fsync()} 调用 \code{sdflush()}。根文件系统、rootfs、devtmpfs 都用这一张表。

\paragraph{ext2（\code{ext2\_iops}）.} ext2 本来就有 inode 号，直接对上：\code{e2\_lookup()} 在目录块里查名字，返回 \code{iget(dev, ino)}；\code{e2\_read\_inode()} 读出磁盘 inode 填进内存 inode，并在 \code{e2.open[]} 表里给这个 inode 号占一个引用；\code{e2\_evict()} 释放这个引用。于是“删除仍被打开的文件”的语义（第~\ref{chap:optional} 章）由 inode 缓存自然驱动：只要还有进程持有这个 inode，它就只是孤儿；最后一个 \code{iput()} 时 \code{evict} 才真正回收。目录读取经 \code{vfs\_dir\_read()}，写入与截断仍走 ext2 自己的外置日志。

\paragraph{按路径的文件系统（\code{pathfs\_iops}）.} FAT32 的磁盘上没有 inode 号，procfs 的对象是现场生成的，netfs 的协议以路径为键。它们共用 \file{vfs.c} 里的一套通用实现：内存 inode 的 \code{path} 字段记下对象在该文件系统内的路径，inode 号取路径的 31 位 FNV 哈希；\code{iget\_path()} 对这类文件系统除了比较 inode 号还比较路径，哈希冲突也不会认错对象。\code{pfs\_lookup()} 把目录路径和名字拼起来（处理 \code{.} 与 \code{..}），问后端 \code{stat} 是否存在；读写、建立、删除、改名都转成后端按路径的调用。三个后端各提供一张小表：

\begin{ccode}
static struct pathfs_ops fat32_pops = {      // kernel/vfs.c
  .stat = fat_vstat, .read = fat_vread, .write = fat_vwrite,
  .readdir = fat_vreaddir, .create = fat_vcreate, .truncate = fat_vtruncate,
  .rename = fat_vrename, .openwrite = fat32openwrite, .fsync = fat_vfsync,
};
static struct pathfs_ops proc_pops  = { .stat = proc_vstat,  .read = proc_vread,  .readdir = proc_vreaddir };
static struct pathfs_ops netfs_pops = { .stat = netfs_vstat, .read = netfs_vread, .readdir = netfs_vreaddir };
\end{ccode}

FAT32 不能原地改写文件，只能追加：\code{pfs\_open()} 要求以写方式打开的文件长度为 0（新建的，或带 \code{O\_TRUNC} 已被截断的），然后用 \code{fat32openwrite()} 取得写句柄，存在 inode 的 \code{fsdata} 里供之后的追加写使用。procfs 和 netfs 只读。

\begin{itemize}
  \item \textbf{procfs}（\code{/proc}）：没有磁盘数据，列目录时遍历进程表生成每个 PID 的目录，读 \code{status} 时持锁生成快照。另有 \code{/proc/mounts}、\code{/proc/cmdline}、\code{/proc/meminfo}、\code{/proc/iomem}、\code{/proc/devices} 等诊断文件；
  \item \textbf{ext2}（\code{/mnt/ext2} 或 \code{/}）：支持 1/2/4\,KiB 块，遇到 ext4 extent 等不兼容特性就拒绝挂载，可以和 Linux 交换文件；可读写，带外置事务日志，见第~\ref{chap:optional} 章；
  \item \textbf{FAT32}（\code{/boot}）：挂载启动分区，支持根目录的读、创建、截断、顺序写和重命名，支持 ASCII 长文件名。这让系统可以在运行时更新自己的内核：\code{tftp} 下载 \code{kernel8-xv6\_wifi.img} 到 \code{/boot}，重启即生效。
\end{itemize}

\subsection{由用户态决定挂载}

挂载策略仿照嵌入式 Linux：内核只负责探测驱动和挂根，\code{init} 读取 \code{/etc/fstab} 决定其余的挂载。首次启动时 \code{init} 创建：

\begin{txtcode}
proc    /proc      procfs ro 0 0
bootfs  /boot      fat32  rw 0 0
ext2    /mnt/ext2  ext2   rw 0 0
\end{txtcode}

然后逐行调用 \code{mount(source, target, fstype, flags)}。内核里的 \code{vfsmount()} 分两步：先按类型登记 \code{super\_block}（procfs 强制只读；ext2 找到起点与 \code{e2.part\_lba} 相同的分区块设备，用它的设备号），再 \code{namei(target)} 找到挂载点目录，调用与 \code{prepare\_namespace()} 相同的 \code{fs\_mount()} 挂进那一张挂载表。启动日志出现 “vfs: mounted fat32 at /boot read-write” 才说明 FAT32 真的挂上了；挂载点忙、或者同一个文件系统已经挂在别处时，打印 “vfs: cannot mount … (busy or already mounted)”，\code{/boot} 就仍是一个空目录。

\section{FAT32 与启动分区}

\end{txtcode}

然后把 \file{kernel8-xv6\_wifi.img} 原样拷到物理地址 \code{0x80000}，才放开 ARM 核（第~\ref{chap:boot} 章）。所以内核镜像必须是裸二进制而不是 ELF，固件也从不理会 xv6 的根文件系统。

\paragraph{第二组由 xv6 内核驱动读.} 两块 Wi-Fi 网卡每次上电都要由主机下载固件：BCM43430/43455 需要 \file{.BIN}（R4 的执行代码）、\file{.TXT}（NVRAM）和 \file{.CLM}（法规数据库），MT7601U 需要 \file{MT7601U.BIN}。驱动在 \code{main()} 里初始化，这时还没有任何进程，更谈不上挂载点，所以它们直接调用 \code{fat32openroot()} 按 8.3 短名在根目录里找文件，再用 \code{fat32readnext()} 顺序读出。这也是挂起 bootfs 的 \code{rootdev\_init()} 必须排在 \code{brcmfmac\_driver\_init()} 之前的原因。

\paragraph{第三组由用户程序经 \code{/boot} 读写.} 进入用户态以后，\code{init} 按 \file{/etc/fstab} 把同一个分区挂到 \code{/boot}（\ref{sec:vfs} 节）。于是 \code{ls /boot}、\code{cat /boot/config.txt} 都走普通的 \code{open/read}；\code{tftpclient} 把新内核下载成 \file{/boot/kernel8-xv6\_wifi.img}，重启即生效；\code{camshot} 把超过 xv6 单文件上限的照片写成 \file{/boot/camera.bmp}，关机后插到电脑上就能看到。

\paragraph{MBR 和分区表.} 整张卡的第 0 扇区是 MBR：偏移 446 起是 4 个 16 字节的分区表项，最后两个字节是签名 \code{0x55 0xAA}。每个表项里第 4 字节是分区类型（\code{0x0B}/\code{0x0C} 是 FAT32），第 8、12 字节是起始 LBA 和扇区数。读分区表的是 \file{rootdev.c} 的 \code{rootdev\_init()}，而不是 FAT32 驱动。它先把四个表项全部打印出来，再分两轮挑选：第一轮找 block 1 带 xv6 superblock 魔数的分区做根文件系统（\code{setup\_raw\_root()}），第二轮把第一个 FAT32 分区的起点交给 \code{fat32mount()}。两轮互不依赖，所以根文件系统和启动分区可以各在各的分区里。FAT32 驱动的工作从 \code{fat32mount()} 拿到分区起点开始。

\paragraph{BPB：分区的第一个扇区.} FAT32 分区的第 0 扇区叫 BPB（BIOS Parameter Block），记录了整个分区的几何参数。\code{fat32mount()} 用到的字段如表~\ref{tab:bpb}。

有了这些字段，任何簇号都能换算成 SD 卡上的绝对扇区号：

\begin{ccode}
fat_lba  = partition_lba + reserved;
data_lba = fat_lba + fats * fat_sectors;
static uint32 cluster_lba(uint32 cluster) {     // 簇号从 2 开始
  return diskmap.data_lba + (cluster - 2) * diskmap.sectors_per_cluster;
}
\end{ccode}

\code{fat32mount()} 对每个字段都做了合法性检查（2 的幂、不越界、不溢出）——SD 卡上的数据是外部输入，一个损坏的 BPB 不应该让内核算出一个指向别处的 LBA 然后去写它。

\subsection{FAT 表与簇链}

FAT 表是一个巨大的 32 位整数数组，下标就是簇号，第 $c$ 项的值是“簇 $c$ 之后的下一个簇”。只有低 28 位有效，高 4 位保留且写入时要保持原值；0 表示空闲，\code{0x0FFFFFF8} 及以上表示链尾（EOC）。一个 512 字节的扇区装 128 项，所以查第 $c$ 项只需读一个扇区：

\begin{ccode}
static uint32 fat_next(uint32 cluster) {
  uint32 sector = diskmap.fat_lba + cluster / 128;   // 128 = 512 / 4
  uint32 pos    = (cluster % 128) * 4;
  if(sdsector(sector, scratch, 0) < 0) panic("fat32: read FAT");
  return le32(scratch + pos) & 0x0fffffffU;
}
\end{ccode}

\code{fat\_set\_next()} 是对应的写操作，它要把同一个扇区在每一份 FAT 里都读改写一遍，保证两份副本一致。图~\ref{fig:fat-chain} 下半部分画的就是一条簇链：从目录项里拿到首簇，然后反复 \code{fat\_next()} 直到 EOC。

目录的内容是一串 32 字节的目录项（图~\ref{fig:fat-chain} 上半部分）。短名目录项里有 8.3 格式的名字（11 字节，大写、空格填充）、属性字节、首簇号（拆成高低两个 16 位字段，这是 FAT16 向 FAT32 扩展时留下的痕迹）和文件大小。扫描目录时，首字节有两个特殊值：\code{0x00} 表示后面再没有目录项，\code{0xE5} 表示这一项已被删除。属性字节的 \code{0x10} 表示子目录，\code{0x08} 表示卷标。

长文件名（LFN）是后来加的：属性等于 \code{0x0F} 的目录项不是文件，而是一片名字，每片装 13 个 UTF-16 字符，倒序排在它所属的短名目录项前面。第一片（物理上最靠前的）序号带 \code{0x40} 标志，表示“最后一片”；每片都存着短名的校验和，以便发现“LFN 和短名不配套”（例如老系统删了短名但留下了 LFN）。\code{fat\_find\_path()} 扫描目录时把遇到的 LFN 片按序号拼进一个缓冲区，遇到短名项时检查三件事——片序号连续到 1、校验和与短名一致、拼出的名字与要找的名字相同（不区分大小写）——满足才算长名匹配；否则再按短名比较。

创建文件时反过来：\code{fat32createfile()} 先用 \code{fat\_make\_short\_alias()} 造一个 \code{KERNEL\~{}1.IMG} 这样的短名（取前 6 个字母数字、加 \code{\~{}1}～\code{\~{}9} 避免重名），算出需要几片 LFN，用 \code{fat\_reserve\_root\_slots()} 在根目录里找到足够的连续空位（不够就给根目录分配新簇），按倒序写入 LFN 片和短名项，最后补一个全 0 的目录项作为结束标记。

本项目的 FAT32 驱动只处理\emph{根目录}：查找、创建、枚举、重命名都在根目录簇链里进行，不支持子目录，LFN 也只支持 ASCII 字符。对启动分区来说这已经足够——上面列出的所有文件都在根目录里。

\file{fat32.c} 的函数可以按图~\ref{fig:fat-calls} 分成四层：

\begin{itemize}
  \item \textbf{挂载}：\code{fat32mount(lba, sectors)} 解析 BPB、读 FSInfo 里的空闲簇提示；\code{fat32\_is\_boot\_sector()} 判断一个扇区是不是 FAT32 引导扇区，\file{rootdev.c} 用它识别“没有分区表、整张卡就是一个 FAT32”的 superfloppy 格式；\code{fat32init()} 只初始化 \code{fat32\_lock}。分区表扫描和 xv6 根分区识别都不在这个文件里。
  \item \textbf{对外接口}：只读的 \code{fat32openroot()}、\code{fat32openpath()}、\code{fat32statpath()}、\code{fat32readdirroot()}、\code{fat32pread()}、\code{fat32readerinit()}/\code{fat32readnext()}；写入的 \code{fat32createfile()}、\code{fat32openwrite()}、\code{fat32writefile()}、\code{fat32truncatefile()}、\code{fat32renamefile()}。VFS 的 \code{fat32\_pops} 把它们包装成按路径的操作，再经 \code{pathfs\_iops} 成为 \code{/boot} 上的 inode 操作（\ref{sec:vfs} 节）。
  \item \textbf{目录与 FAT}：上一小节的查找和 LFN 函数，以及 \code{fat\_next()}、\code{fat\_set\_next()}、\code{fat\_alloc\_cluster()}、\code{fat\_free\_chain()}、\code{fat\_mark\_fsinfo\_unknown()}。
  \item \textbf{文件扇区映射}：\code{fat32mapfile()} 记下根目录中某个文件的整条簇链，\code{fat32mapsector()} 把“文件内第 $s$ 个扇区”换成卡上的扇区号。它们只为兼容早期把根镜像存成 \code{FS.IMG} 文件的旧卡而保留，调用者是 \file{rootdev.c}。FAT32 只回答“这个扇区在哪里”，从不解释扇区里的 xv6 数据。
\end{itemize}

两个读接口的区别值得一提。\code{fat32pread(file, offset, …)} 是无状态的：每次调用都从首簇沿链走 $\lfloor\text{offset}/\text{簇大小}\rfloor$ 步，适合 VFS 偶尔的随机读。如果用它按 512 字节分块读一个 600\,KiB 的 Wi-Fi 固件，总共要走 $O(n^2)$ 次 \code{fat\_next()}。\code{fat32reader} 则记住当前簇和簇内偏移，顺序读时每跨一个簇只查一次 FAT——固件下载就用它。

\subsection{写入：分配、追加与截断}

\code{fat32writefile()} 只支持追加：要求写入位置正好等于文件当前大小。写入过程是：

\begin{enumerate}
  \item 重新按路径查找目录项，核对首簇和大小与调用者手里的 \code{fat32\_file} 一致，防止文件已被别人改过；
  \item 写入跨进新簇时调用 \code{fat\_alloc\_cluster()}：从 FSInfo 提示的位置开始找 FAT 值为 0 的项，把它标成 EOC（每份 FAT 都写），把这一簇清零；再用 \code{fat\_set\_next()} 把它挂到链尾；
  \item 按扇区写数据：整扇区直接写，不满一个扇区的先读出来再改再写回；
  \item 最后一次性更新目录项里的首簇和大小。
\end{enumerate}

\code{fat32truncatefile()}（\code{O\_TRUNC}）的顺序恰好相反：先把目录项的首簇和大小清零并写回，再释放旧簇链。这个顺序的意义在于断电时的后果：先改目录项，最坏情况是旧簇成了没人引用的“丢失簇”，浪费一点空间；如果先释放簇链，断电后目录项会指向已被标为空闲、随时可能分给别人的簇，那才是真正的损坏。分配和释放之后，\code{fat\_mark\_fsinfo\_unknown()} 把 FSInfo 里的空闲簇计数标成“未知”（\code{0xFFFFFFFF}），只更新“下一个空闲簇”提示，避免留下一个过时的计数让别的系统误信。

两处性能问题都是真机上暴露出来的，修法相同——缓存当前 FAT 扇区：
\begin{itemize}
  \item \code{fat\_alloc\_cluster()} 最初对每个候选簇调用一次 \code{fat\_next()}，同一个扇区要重复读 128 次，根目录一长就像卡死了一样；现在扫描时只在跨扇区时才读；
  \item \code{fat\_free\_chain()} 最初对每个簇做一次读和两份 FAT 的读改写，截断一张 320$\times$240 的 BMP 要五百多次 SD 事务（第~\ref{chap:drivers} 章 \ref{sec:cam-bugs} 小节）；现在在一个扇区内批量清除链项，换扇区时才把整扇区写到每份 FAT。
\end{itemize}

\paragraph{并发与局限.} 所有接口都持同一把自旋锁 \code{fat32\_lock}，共用一个 512 字节的 \code{scratch} 扇区缓冲，没有块缓存，也没有日志。路径解析、LFN 字符、目录槽这些较大的临时数组也放在一个静态工作区 \code{fat\_work} 里，而不是放在栈上——每个进程的内核栈只有 4\,KiB，它们曾经把创建文件的调用链撑爆（第~\ref{chap:drivers} 章 \ref{sec:cam-bugs} 小节）；既然有 \code{fat32\_lock} 串行化，一个工作区就够用。这让实现很简单，代价也很清楚：持锁期间 \code{sdsector()} 以 PIO 方式等待 SD 卡，一次大文件写会长时间占着这把锁；同一时间只能有一个写者；写入途中断电可能损坏分区。启动分区平时几乎只读，偶尔更新内核或写一张照片，这些代价是可以接受的，但修改它之前最好备份。

\section{xv6 根文件系统：superblock、inode 与目录}
\label{sec:xv6fs}

前一节分析了启动分区上的 FAT32，这一节用同样的方法看 p2 上的 xv6 根文件系统：它怎么被认出来，磁盘上每一块放的是什么，文件和目录怎样表示，一个路径怎样一步步变成 SD 卡上的扇区。\ref{sec:rootfs} 节讲过根文件系统可以放在哪里；这里只讨论现在的“原始分区”方式。

\subsection{根文件系统怎样被认出来}

\code{rootdev\_init()} 扫描 MBR 时，对每个既不是 FAT32 也不是扩展分区的主分区调用 \code{setup\_raw\_root()}（两者都在 \file{kernel/rootdev.c}）：

\begin{ccode}
static int setup_raw_root(uint32 start, uint32 sectors) {
  // xv6 的第 1 块是 superblock；块大小 1024，所以它在分区起点之后第 2 个扇区
  if(start == 0 || sectors < FSSIZE * SECTORS_PER_BLOCK ||
     sdsector(start + SECTORS_PER_BLOCK, sector, 0) < 0 ||
     le32(sector) != FSMAGIC || le32(sector + 4) != FSSIZE)
    return -1;
  root.mode = ROOT_RAW;
  root.lba = start;
  root.sectors = sectors;
  return 0;
}
\end{ccode}

判断只看两样东西：superblock 开头的魔数 \code{0x10203040}，以及紧跟着的 \code{size} 是否等于内核编译时的 \code{FSSIZE}。MBR 里的分区类型不作数——macOS 的 \code{diskutil} 只能把这个分区建成 Linux 的 \code{0x83} 类型，和真正的 ext2 分区一样，靠魔数才能分开。\code{size} 的检查同样重要：如果有人改了 \code{FSSIZE} 重新编译内核却没重新烧 \code{fs.img}，这里会拒绝，而不是让新内核去解释旧格式的磁盘。识别成功后启动日志打印：

\begin{txtcode}
rootdev: raw xv6 root p2 lba=208896 sectors=819200 size=400 MiB
\end{txtcode}

此后块缓存的每一次读写都经过 \code{rootdev\_rw()}：

\begin{ccode}
void rootdev_rw(struct buf *b, int write) {         // kernel/rootdev.c
  uint32 first = b->blockno * SECTORS_PER_BLOCK;    // 1 块 = 2 扇区
  gate_enter();                                     // /dev/sdroot 更新时在此挡住
  for(int i = 0; i < SECTORS_PER_BLOCK; i++)
    if(sdsector(root_sector_lba(first + i),
                b->data + i * SECTOR_SIZE, write) < 0)
      panic(write ? "rootdev: write block" : "rootdev: read block");
  gate_exit();
}
\end{ccode}

原始分区模式下 \code{root\_sector\_lba()} 只做一次加法：扇区号 $=$ \code{root.lba} $+$ 块号 $\times 2 + i$。整条路径不经过 \file{fat32.c} 的任何函数。分区有 400\,MiB，文件系统只用前 32\,MiB；可分配多少块由 superblock 决定，与分区大小无关。

\begin{ccode}
#define IPB           (BSIZE / sizeof(struct dinode))   // 每块 16 个 inode
#define IBLOCK(i, sb) ((i) / IPB + sb.inodestart)       // inode i 所在的块
#define BPB           (BSIZE * 8)                       // 每个位图块管 8192 块
#define BBLOCK(b, sb) ((b) / BPB + sb.bmapstart)        // 块 b 的位所在的位图块
\end{ccode}

\paragraph{日志区.} 30 块中第一块是日志头 \code{struct logheader}：一个计数 \code{n} 加上 \code{n} 个“这些块属于哪个目标块号”。其余是被修改的块的副本。提交时先写副本、再写日志头（这一写就是提交点）、再把副本拷回原位、最后把 \code{n} 清零；\code{fsinit()} → \code{initlog()} 在启动时检查日志头，\code{n} 不为 0 就重做一遍。

\paragraph{位图.} 每一位对应一块，1 表示已用。\code{mkfs} 把前 \code{freeblock} 块（元数据加上镜像里已经写入的全部文件内容）一次性标成已用；运行时 \code{balloc()} 从头扫描位图找第一个 0 位，置 1、\code{log\_write}、再把新块清零。早期 \code{FSSIZE} 只有 1000 块时，光是打包进镜像的程序就用掉 986 块，首次启动创建 \code{/etc} 配置时 \code{balloc} 找不到 0 位，panic “out of blocks”——这就是 \code{FSSIZE} 改成 32768 的原因。

每个文件、目录和设备节点都由一个 64 字节的磁盘 inode 描述（图~\ref{fig:xv6-inode}）。它不包含文件名——名字在目录里——只有类型、链接数、大小和数据块的位置。内存里的 \code{struct inode} 在此之外再加上 \code{dev}、\code{inum}、引用计数 \code{ref}、睡眠锁和 \code{valid} 标志（是否已从磁盘读入）。\code{iget()} 只在 inode 缓存里占一个槽、不读盘；\code{ilock()} 第一次加锁时才 \code{bread(IBLOCK(...))} 把磁盘 inode 拷进来；修改后 \code{iupdate()} 写回。

块映射由 \code{bmap()} 完成：

\begin{ccode}
static uint bmap(struct inode *ip, uint bn) {
  uint addr, *a;
  struct buf *bp;
  if(bn < NDIRECT){                                   // 前 12 块：直接块
    if((addr = ip->addrs[bn]) == 0)
      ip->addrs[bn] = addr = balloc(ip->dev);
    return addr;
  }
  bn -= NDIRECT;
  if(bn < NINDIRECT){                                 // 之后 256 块：经间接块
    if((addr = ip->addrs[NDIRECT]) == 0)
      ip->addrs[NDIRECT] = addr = balloc(ip->dev);
    bp = bread(ip->dev, addr);
    a = (uint*)bp->data;
    if((addr = a[bn]) == 0){
      a[bn] = addr = balloc(ip->dev);
      log_write(bp);
    }
    brelse(bp);
    return addr;
  }
  panic("bmap: out of range");
}
\end{ccode}

所以单个文件最大 $12+256=268$ 块，即 268\,KiB。这是 xv6 根文件系统最明显的限制：Wi-Fi 固件、640$\times$480 的 BMP（900\,KB）、原始帧（375\,KB）都放不下，只能放在 FAT32 的 \code{/boot}（\ref{sec:fat32} 节）。

根文件系统里几个特殊的 inode 号：1 号永远是根目录（\code{ROOTINO}），\code{namex()} 遇到以 \code{/} 开头的路径就从它开始；2 号是 \code{mkfs} 建的 \code{/bin}；之后是按 \code{Makefile} 顺序装入的每个用户程序。\code{init} 是唯一一个在根目录下也有名字的程序（启动代码执行的是 \code{exec("init")}），所以 \code{/init} 和 \code{/bin/init} 是同一个 inode 的两个目录项，\code{mkfs} 把它的 \code{nlink} 设为 2。

路径查找是 \code{namex()}，图~\ref{fig:xv6-namei} 画的是 \code{namei("/bin/ls")}：

\begin{ccode}
if(*path == '/') ip = iget(ROOTDEV, ROOTINO);        // 绝对路径从 inode 1 开始
else             ip = idup(myproc()->cwd);            // 相对路径从当前目录开始
while((path = skipelem(path, name)) != 0){           // 依次取出 "bin"、"ls"
  ilock(ip);
  if(ip->type != T_DIR){ iunlockput(ip); return 0; }
  if(nameiparent && *path == '\0'){ iunlock(ip); return ip; }   // 停在父目录
  if((next = dirlookup(ip, name, 0)) == 0){ iunlockput(ip); return 0; }
  iunlockput(ip);
  ip = next;
}
\end{ccode}

注意加锁的顺序：每一步只锁当前目录，查到下一级以后先 \code{iunlockput()} 当前目录再进入下一级，任何时刻最多持有一把 inode 锁，所以不会因为两个进程以相反顺序查找路径而死锁。\code{nameiparent()} 在最后一个分量之前停下，返回父目录并把最后一个名字留给调用者——\code{create}、\code{unlink}、\code{link} 都需要它。

根目录的内容分两部分：\code{mkfs} 写入的 \code{.}、\code{..}、\code{bin}、\code{init}；以及启动时创建的 \code{dev}（内核在 \code{prepare\_namespace()} 里建出这个空目录，再把 devtmpfs 挂上去，\code{console}、\code{ttyS0}、\code{input/event0}、\code{video0}、\code{sdroot} 等设备节点都在 devtmpfs 里）、由 \code{init} 首次启动时创建的 \code{etc}（\code{fstab} 等配置）、\code{proc}、\code{boot}、\code{mnt/ext2}、\code{root}、\code{usr/bin}。其中 \code{dev}、\code{proc}、\code{boot}、\code{mnt/ext2} 只是空目录，挂载以后会被挂载表“盖住”（\ref{sec:vfs} 节）。设备节点是 \code{type=3} 的 inode，不占数据块，只在 \code{major}/\code{minor} 里记下交给哪个驱动。

\subsection{从路径到 SD 扇区}

把这一节和前面几节串起来，读 \code{/bin/ls} 的第 0 字节要经过这些层：

\begin{txtcode}
namei("/bin/ls")             -> inode m（经 inode 1、inode 2 的目录内容）
readi(ip, ..., off=0, n)     -> bn = off / 1024 = 0
bmap(ip, 0)                  -> 块号 B = ip->addrs[0]
bread(ROOTDEV, B)            -> 块缓存未命中，调用 rootdev_rw(b, 0)
root_sector_lba(2B), (2B+1)  -> 扇区 208896 + 2B 和 208896 + 2B + 1
sdsector(lba, buf, 0)        -> SDHOST CMD17，PIO 读 512 字节
\end{txtcode}

一个 1\,KiB 的 xv6 块对应两个 512 字节扇区。写入的路径与此相同，只是中间多了日志：\code{writei()} 修改的块经 \code{log\_write()} 记入日志，\code{end\_op()} 提交时才真正经 \code{rootdev\_rw()} 写到 SD 卡。

\subsection{\code{mkfs} 怎样生成 \code{fs.img}}

\code{mkfs} 是一个在宿主机上运行的普通 C 程序，它和内核共用 \file{kernel/fs.h}，因此磁盘格式只有一份定义：

\begin{enumerate}
  \item 按 \code{FSSIZE}、\code{NINODES}、\code{LOGSIZE} 算出各区大小，把 32768 块全部写 0，再在第 1 块写入 superblock；
  \item \code{ialloc(T\_DIR)} 得到 inode 1，写入 \code{.} 和 \code{..}（都指向自己）；再建 inode 2 作为 \code{/bin}，在根目录里加 \code{bin} 项；
  \item 对命令行上的每个程序（\code{\_ls}、\code{\_cat}…去掉前缀下划线）分配一个 inode、在 \code{/bin} 里加目录项、用 \code{iappend()} 把文件内容逐块追加——它和内核的 \code{bmap()} 一样，前 12 块直接放、之后经间接块；\code{init} 额外在根目录里加一项；
  \item 把两个目录的大小取整到整块；最后 \code{balloc(freeblock)} 把已经用掉的前 \code{freeblock} 块在位图里标成 1。
\end{enumerate}

\code{mkfs} 只按顺序分配块和 inode，不需要日志，也不处理删除；所有整数都用 \code{xint()}/\code{xshort()} 写成小端序，与 AArch64 内核一致。

\subsection{在系统里更新根文件系统}

根文件系统的格式一旦改动（例如 \code{DIRSIZ} 从 14 改成 30），就必须整体重写 p2。最初只能把 SD 卡拔到电脑上 \code{dd}；后来内核增加了一个受保护的字符设备 \code{/dev/sdroot}，它只允许写启动时 \code{setup\_raw\_root()} 选中的那个分区，绝不暴露整张卡。更新流程是：

\begin{shcode}
/bin/tftpclient 192.168.0.195 fs.img          # 下载到 /boot（FAT32）
/bin/dd if=/boot/fs.img of=/dev/sdroot bs=32768
\end{shcode}

\code{dd} 在写之前先检查镜像大小恰好是 \code{FSSIZE}$\times$\code{BSIZE}、把整个镜像读进内存并校验 superblock 的魔数、大小和各区起点——因为一旦开始覆盖 p2，就再也不能从旧的根文件系统读任何东西，连 \code{dd} 自己的代码也不行（用户程序是静态链接的，已全部在内存里）。打开 \code{/dev/sdroot} 时内核冻结根文件系统：不再接受新的事务，等已有事务提交、读者退出；然后每写一个扇区就读回比较一次。结束时打印：

\begin{txtcode}
sdroot: verified 32/32 MiB
sdroot: update complete and verified; reboot now
dd: 33554432 bytes installed and read-back verified
dd: root filesystem is frozen; power-cycle Raspberry Pi now
\end{txtcode}

冻结是单向的，无论成败都必须断电重启——内存里的块缓存和 inode 缓存描述的是旧磁盘，不能再拿来解释新磁盘。

\subsection{步骤}

以 macOS 为例（\code{disk4} 必须先用 \code{diskutil list} 确认，写错磁盘会毁掉数据）：

\begin{shcode}
# 1. 卸载整张卡并重新分区
diskutil unmountDisk force /dev/disk4
diskutil partitionDisk /dev/disk4 4 MBR \
  FAT32 BOOTFS 100MiB  UFSD_EXTFS XV6FS 400MiB \
  UFSD_EXTFS EXT2 R    UFSD_EXTFS SPFS 500MiB

# 2. 写入 xv6 根文件系统（只能写分区 2，绝不能写整卡 /dev/rdisk4）
make fs.img
make install-rpi3-rawfs RPI3_XV6_DEV=/dev/rdisk4s2

# 3. 把分区 3 格式化成不带 ext4 特性的 ext2
sudo mke2fs -F -t ext2 -L EXT2 /dev/rdisk4s3

# 4. 在 BOOTFS 中放入树莓派官方固件（bootcode.bin、start.elf、fixup.dat 等），
#    然后安装内核、config.txt 和 Wi-Fi 固件
make install-rpi3 RPI3_XV6_DEV=/dev/rdisk4s2
\end{shcode}

\code{Makefile} 对 \code{RPI3\_XV6\_DEV} 做了检查：变量为空时只更新内核、配置和固件，并给出警告；不是 \code{/dev/diskNsM} 形式的分区设备则拒绝执行。这些防护是吃过亏之后加上的——\code{dd} 写错一个字母就会覆盖整张卡的分区表。

\subsection{日常更新}

改了内核之后不必每次拔卡：运行 \code{make}，内核会被拷到宿主机的 TFTP 目录；在树莓派上执行

\begin{shcode}
tftp 192.168.0.195 kernel8-xv6_wifi.img
\end{shcode}

文件就会下载到 \code{/boot}（FAT32 启动分区），重启后生效。只有用户程序或文件系统格式变化时，才需要重新烧录分区 2。
