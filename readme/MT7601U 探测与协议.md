# MT7601U 探测与协议

按一次真机启动的日志，把 MT7601U USB 无线网卡从“被枚举”到“DHCP 拿到地址”的每一步对到函数调用上：USB 拓扑与三种描述符、驱动探测时序、主机与芯片之间的报文格式、802.11 关联和 WPA2 四次握手，以及调试过程中发现并修好的问题。

## 1. USB 拓扑：网卡挂在哪里

树莓派 3B 的 DWC2 控制器只有一个根端口，板上固定接着 SMSC LAN9514（集线器 + 以太网）。

```
dwc2: host hprt=100f                         HPRT0：bit0 已连接、bit2 已使能、bit12 上电
dwc2: root device class=9 vid=424 pid=9514   集线器，SET_ADDRESS 1，SET_CONFIG，各端口 SET_PORT_FEATURE(POWER)
dwc2: hub port 1 status=101 change=1         0x0101 = 已连接 + 上电；change bit0 = 连接变化
dwc2: hub port 1 after-reset status=503      SET_PORT_FEATURE(RESET) 后：再加上已使能、高速（bit10）
dwc2: hub port=1 child class=255 … pid=ec00  板载以太网，addr 2，没有驱动，跳过
dwc2: hub port 2 status=100 change=0         只有上电位：空端口（轮询 50 次、每次 10 ms 后放弃）
dwc2: hub port 3 status=100 change=0         同上
dwc2: hub port 4 status=101 change=1         网卡插在这里（上一份日志里是端口 2）
dwc2: hub port=4 child class=0 vid=148f pid=7601   is_mt7601() 命中，addr 3，停止扫描
```

新设备复位后的地址是 0：主机先在 addr 0 读 8 字节设备描述符拿到 EP0 最大包长，再 `SET_ADDRESS`，然后才读完整描述符。复位后状态里的 bit10（高速，480 Mbit/s）决定了后面 bulk 端点的最大包长是 512。

## 2. 三种描述符

### 2a. 设备描述符（18 B，bDescriptorType=1）

`usb-enum: device … usb=201 class=0 subclass=0 protocol=0 mps0=64 vid=148f pid=7601 device=0 configs=1`

| 字段 | 值 | 含义 |
| --- | --- | --- |
| bcdUSB | 0x0201 | USB 2.01 |
| bDeviceClass/SubClass/Protocol | 0/0/0 | 设备级不定类别，看接口描述符 |
| bMaxPacketSize0 | 64 | EP0 每包 64 B |
| idVendor/idProduct | 148f/7601 | Ralink（联发科）MT7601U；`is_mt7601()` 和驱动 `id_table` 都按它匹配 |
| bNumConfigurations | 1 | 只有一种配置 |

### 2b. 配置描述符（9 B，type 2）及其后附带的整块

`usb-enum: config addr=3 value=1 total=74 interfaces=1 attributes=80 maxpower=160 mA`

| 字段 | 值 | 含义 |
| --- | --- | --- |
| wTotalLength | 74 | 配置 + 接口 + 全部端点描述符的总长 |
| bNumInterfaces | 1 | 一个接口 |
| bConfigurationValue | 1 | `SET_CONFIGURATION(1)` 用的编号 |
| bmAttributes | 0x80 | 总线供电，不支持远程唤醒 |
| bMaxPower | 80 | 单位 2 mA，即 160 mA |

`dwc2_init()` 分两步读：先 `GET_DESCRIPTOR(CONFIG, 9)` 拿到 wTotalLength，再 `GET_DESCRIPTOR(CONFIG, 74)` 一次读完。74 = 9（配置）+ 9（接口）+ 8 × 7（端点）。

### 2c. 接口描述符（9 B，type 4）

`usb-enum:  interface=0 alt=0 eps=8 class=255 subclass=255 protocol=255`：唯一接口、唯一备用设置、8 个端点（不含 EP0），类别全是 0xFF（厂商自定义）。没有通用类驱动可用，只能按 VID/PID 匹配专用驱动；HID 键盘则是 class 3，可以按类别匹配。

### 2d. 端点描述符（7 B，type 5）

| bEndpointAddress | 方向 | bmAttributes | wMaxPacketSize | Linux 中的用途 | 本驱动 | DWC2 通道 |
| --- | --- | --- | --- | --- | --- | --- |
| 0x84 | IN（bit7=1），EP4 | 2 bulk | 512 | 802.11 数据帧（聚合） | 数据接收，4 个 16 KiB 缓冲 | ch4 异步（初始化期间 ch3 同步清空） |
| 0x85 | IN，EP5 | bulk | 512 | MCU 命令应答 | MCU 应答，命令发出前预挂 | ch4 异步 |
| 0x08 | OUT，EP8 | bulk | 512 | in-band 命令 | 固件、MCU 命令、所有 802.11 帧 | ch5 同步 |
| 0x04–0x07 | OUT | bulk | 512 | WMM 队列 BE/BK/VI/VO | 未用 | — |
| 0x09 | OUT | bulk | 512 | HCCA/管理 | 未用 | — |

bmAttributes 低 2 位是传输类型（0 控制、1 等时、2 bulk、3 中断）；高速 bulk 端点必须是 512 B；bulk 的 bInterval 无意义（0）。

`dwc2_init()` 的选取规则（解析循环跳过非端点描述符和非 bulk 端点）：第一个 bulk IN → `bulk_in_ep`（EP4），第二个 → `bulk_in_ep2`（EP5），第一个 bulk OUT → `bulk_out_ep`（EP8）。三者缺一就放弃这个设备，然后 `SET_CONFIGURATION(1)`，打印 `MT7601U configured; bulk-in=4,5/512 bulk-out=8/512`。

DWC2 没有通用的 URB 调度，端点固定绑在主机通道上：ch0 做 EP0 控制传输，ch3 做同步 bulk IN（每次最多等 2 ms），ch4 做异步 bulk IN（5 个槽位：EP4 的 4 个 + EP5 的 1 个，轮流调度），ch5 做 bulk OUT，ch6 留给 HID 键盘的中断端点。

## 3. 探测时序：函数调用链

```
main()                                    CPU0，中断尚未打开，调度器尚未运行
  usb_bus_init()                          bus_register(&usb_bus)
  dwc2_driver_init() → dwc2_probe() → dwc2_init()
    usb_firmware_power_on()               ① VideoCore 邮箱给 USB 上电
    get_device_descriptor / control()     ② 集线器 addr 1；端口上电、GET_PORT_STATUS、复位
    is_mt7601(vid, pid)                   ③ 端口 4 命中
    control(GET_DESCRIPTOR CONFIG 9 / 74), 解析端点, control(SET_CONFIGURATION 1)
    usb_device_register(&usb_child)       ④ 设备进总线；此时还没有 mt7601u 驱动
  ...
  rootdev_init()                          挂 FAT32 /boot（固件在这里）
  brcmfmac_driver_init()                  板载 SDIO 网卡（BCM43430/43455）
  mt7601u_driver_init()
    usb_register_driver() → driver_register()
      → usb_match()                       id_table: 148f:7601
      → usb_probe() → mt7601u_probe(udev)

          mt7601u_validate_firmware()      ⑤ /boot/MT7601U.BIN：32 B 头 + ILM 45380（含 64 B IVB）+ DLM 0
          mt7601u_load_firmware()
            mt7601u_dma_fw_range() → mt7601u_dma_fw_chunk() ×4   EP8 bulk OUT，14336×3 + 2308
            DEV_MODE 0x12 + IVB；poll COM_REG0 == 1             MCU firmware running
          mt7601u_read_eeprom() → mt7601u_efuse_read_block()  ⑥ MAC、频偏、RSSI、LNA
          mt7601u_basic_hw_init()             WLAN 时钟/PLL、复位 MAC、USB DMA 与聚合、MAC 地址、RF R12
          mt7601u_mcu_channel_init()          MCU FUN_SET(Q_SELECT=1)：此后应答走 EP5
          mt7601u_full_hw_init()           ⑦
            MAC 表 44 项 (write32)、BBP 表 59 项 (bbp_write)
            WCID 地址表 / 共享密钥模式 / WCID 属性表 初始化（同 Linux init_hardware）
            RF 表 138 项 (rf_write)
            calibrate(R) → rf_write(R4 VCO) → calibrate(TXDCOC) → rxdc_cal()
              → set_bw_filter(1) → calibrate(LOFT, TXIQ, RXIQ, DPD) → rxdc_cal()
            endpoints_ready = 1；RX 过滤 0x1400；MAC_SYS_CTRL = 0x0c（开收发）
          mt7601u_set_channel(1)           ⑧ mcu_write_pairs(RANDOM_WRITE, RF R17–R20)
                                              bbp_write(62–64)、VCO 校准、set_bw_filter(0)
          wpa_pbkdf2()                        PMK 预先算好（4096 轮 HMAC-SHA1）
          netif_napi_add / napi_enable / bulk_rx_arm(EP4) ×4
          queue_delayed_work(state_work)      probe 返回，后面交给状态机
```

每条需要应答的 MCU 命令都走 `mt7601u_mcu_command()`：

```
mt7601u_mcu_command(cmd, payload, wait=1)
  seq = ++mcu_seq & 0xf
  bulk_rx_arm(EP5, mt_mcu_resp)             先挂好应答缓冲（Linux 的 resp URB 也是这样）
  dwc2_usb_bulk(EP8, TXINFO|payload|0)      发命令
  循环 ≤1500 ms：
    bulk_rx_complete(EP5)                   中断未开时也直接读 HCINT(4) 判断完成
    没完成 → mt7601u_drain_data_ep()         EP4 环还没挂时，同步读空 EP4（丢弃）
    完成 → 检查 seq 和事件类型，不符则重挂 EP5 继续等
```

日志 `MCU cmd 12 seq 9 answered after 2 ms; drained 1684 bytes from EP4` 就是这段逻辑的现场：MAC 已经在收信标，EP4 里积压了 1684 字节，读走后 EP5 的应答立即出来。

## 4. 通信协议：主机和芯片之间的报文

### 4a. 寄存器读写：EP0 厂商请求

```
读  0xC0  bRequest=7 (MULTI_READ)  wValue=0          wIndex=reg    wLength=4  → 小端 4 B
写  0x40  bRequest=2 (WRITE)       wValue=v & 0xffff wIndex=reg    wLength=0
    0x40  bRequest=2               wValue=v >> 16    wIndex=reg+2  wLength=0
其它：bRequest=0x42 写 FCE 寄存器；bRequest=1 (DEV_MODE) 复位/启动 MCU
```

BBP 和 RF 寄存器经间接端口访问：把“寄存器号 + 值 + BUSY/KICK”写进 `BBP_CSR_CFG`（0x101c，bit16 READ、bit17 BUSY、bit19 RW_MODE）或 `RF_CSR_CFG`（0x0500，bit30 WR、bit31 KICK），再轮询忙位。换信道时频率表改由 MCU 的 `RANDOM_WRITE` 写（地址加 `0x80000000` 表示 RF），因为运行中的固件也在用 `RF_CSR_CFG`。

### 4b. bulk OUT：同一个 EP8，靠 TXINFO 分流

| 包 | TXINFO 关键位 | 后续内容 |
| --- | --- | --- |
| 固件块 | 端口 2（CPU_TX）+ 长度 | ≤14336 B 固件；发前写 FCE_DMA_ADDR/LEN，发后 CPU_DESC_IDX+1，等 COM_REG1 bit31 |
| MCU 命令 | bit30 命令、端口 2、命令号（bit20–26）、序号（bit16–19）、长度 | 载荷：FUN_SET {1,1}、CALIBRATE {id,value}、RANDOM_WRITE {addr,value}… |
| 802.11 帧 | bit19 802.11、WIV（不需硬件加 IV 时置位）| 20 B TXWI（速率、ACK、WCID、MPDU 长度）+ MPDU |

每个包末尾补 4 字节 0，中间按 4 字节对齐。管理帧和 EAPOL 用 `WIV=1`（明文）；握手后数据帧 Protected=1、`WIV=0`、WCID 1，由硬件按 WCID 的 IV 表生成 CCMP 头并加密。

用到的 MCU 命令：

| 命令 | 号 | 用途 |
| --- | --- | --- |
| FUN_SET | 1 | Q_SELECT=1：应答走 EP5 |
| RANDOM_WRITE | 12 | {地址, 值} 对；`0x80000000 + reg` 写 RF bank 0 |
| CALIBRATE | 31 | id：1 R、4 LOFT、5 TXIQ、6 BW、7 DPD、8 RXIQ、9 TXDCOC |

### 4c. bulk IN：EP4 聚合包、EP5 应答

EP4 一次 bulk IN 带回多段，每段 = 4 B 长度 + 28 B RXWI + MPDU + 4 B 尾。`mt7601u_rx_parse()` 逐段拆开：

```
rx data fc=4208 rxinfo=1520a2 len=76 hdr=32 llc=aa aa 3 0 0 0 8 0
        │       │                    │       └ LLC/SNAP + 0x0800（IPv4）
        │       │                    └ 24 B 802.11 头 + 8 B CCMP 头
        │       └ bit5 组播、bit7 本 BSS、bit16 已解密、PN_LEN(bit19–21)=2：硬件不剥 CCMP 头
        └ 数据帧、From-DS、Protected
```

管理帧交 `rx_mgmt()`，数据帧交 `rx_data()`（EAPOL 交 `rx_eapol()`）。数据帧转换成以太网帧（目的 = addr1，源 = addr3，类型 = LLC 后两字节），进 8 帧环形队列，再在 NAPI 上下文里拷出、释放锁后 `net_rx_dev()` 交给协议栈（和 brcmfmac 的 `brcmf_napi_poll()` 一样）。

EP5 只收 MCU 应答：前 4 字节 bit16–19 是序号、bit20–23 是事件类型（0 = 完成）。

## 5. 启动日志分析：USB 总线上发生了什么

第 3 节给出了函数调用链，第 4 节给出了报文格式；下面把 `mt7601u_probe()` 打印的每一行，翻译成它在 USB 上实际发出的传输。所有传输都发往**设备地址 3**，区别只在端点。

**先认识两种传输。**

控制传输（EP0）分三个阶段：SETUP（8 B：bmRequestType、bRequest、wValue、wIndex、wLength）→ 可选的 DATA → 方向相反的零长度 STATUS。MT7601U 的寄存器都用厂商请求访问：

| 操作 | bmRequestType | bRequest | wValue | wIndex | 数据 |
| --- | --- | --- | --- | --- | --- |
| 读 32 位寄存器 | 0xC0（设备→主机、厂商） | 7 MULTI_READ | 0 | 寄存器地址 | IN 4 B（小端） |
| 写 32 位寄存器 | 0x40（主机→设备、厂商） | 2 WRITE | 低 16 位 | 地址 | — |
| 　（第二次） | 0x40 | 2 | 高 16 位 | 地址+2 | — |
| 写 FCE（固件 DMA） | 0x40 | 0x42 | 值 | 地址 | — |
| 复位/启动 MCU | 0x40 | 1 DEV_MODE | 模式 | 0 | 可带数据 |

读一个寄存器 = 1 次控制传输，写一个 = 2 次。

bulk 传输（EP8 OUT、EP4/EP5 IN）每包最多 512 B，DWC2 的 DMA 自动切包，PID 在 DATA0/DATA1 间交替（toggle）以发现丢包。IN 方向主机不停发 IN 令牌，设备没数据就回 NAK；收满或收到短包（<512 B）就结束。EP8 上每个包 = 4 B TXINFO + 内容 + 4 B 0，TXINFO 告诉芯片这是固件、MCU 命令还是 802.11 帧。

**① `USB device 148f:7601 ASIC=76010001 MAC=76010500`** —— 两次 EP0 控制读：

```
SETUP C0 07 0000 0000 0400 → IN 01 00 01 76 → STATUS   0x0000 ASIC_VERSION = 0x76010001
SETUP C0 07 0000 0010 0400 → IN 00 05 01 76 → STATUS   0x1000 MAC_CSR0    = 0x76010500
```

VID/PID 是 dwc2 从设备描述符读的；这里再读芯片自己的版本寄存器，确认高 16 位是 0x7601。

**② `driver WPA2-v4 …`** —— 只是打印，不走 USB。

**③ `firmware v0.1.0 build=7640 size=45412 validated`** —— 也不走 USB：从 SD 卡 FAT32 读 `/boot/MT7601U.BIN`，检查 32 B 头（ILM 45380 B，其中前 64 B 是 IVB 中断向量；DLM 0）。32 + 45380 = 45412。

**④ `ILM firmware upload 14336/… 45316/45316`** —— 固件写进 MCU 的指令内存，分 4 块（14336 × 3 + 2308）。每块是一组：

```
EP0  40 42 a840 0230   ┐ FCE_DMA_ADDR / FCE_DMA_LEN：告诉芯片 DMA
EP0  40 42 …    0232   │ 下一包写到 MCU 内存哪里、多长
EP0  40 42 …    0234   │
EP0  40 42 …    0236   ┘
EP8  bulk OUT 2316 B:  04 09 00 10 | 2308 B 固件 | 00 00 00 00
EP0  读 0x09a8 = 3，写 0x09a8 = 4      CPU_DESC_IDX 加一：“新的一块到了”
EP0  读 0x0734 = 0xc9040000           COM_REG1 bit31 = 1：这块收完了
```

TXINFO `04 09 00 10` 即小端 0x10000904：低 14 位 0x904 = 2308 是长度，bit27–29 = 2 表示发往 CPU_TX 端口（交给 FCE/DMA，而不是射频）。一块 14336 B 加首尾 8 B 共 14344 B，DWC2 把它切成 28 个 512 B 包加一个 8 B 短包。

**⑤ `MCU firmware running`**

```
EP0  SETUP 40 01 0012 0000 4000 + DATA OUT 64 B（IVB）  DEV_MODE 0x12：带中断向量启动 MCU
EP0  读 0x0730 → 1                                      COM_REG0 == 1：固件在跑
```

这是带数据阶段的控制写：SETUP、64 B DATA OUT、零长度 IN STATUS。

**⑥ `EEPROM ver=d … permanent mac=90:de:80:14:95:94`** —— eFuse 每 16 B 一块：读 EFUSE_CTRL(0x24) → 写入块地址和 KICK（两次 16 位写）→ 轮询 KICK 清零 → 读 4 个数据寄存器（0x28–0x34）。一块约 8–10 次控制传输，读满 256 B 约 150 次。偏移 4 是 MAC，`freq=96` 是晶振频偏，`lna` 是接收增益，`temp` 是参考温度。

**⑦ `MAC/BBP/RF bootstrap ready; rx-ep=4 data, 5 MCU`** —— `mt7601u_basic_hw_init()`，仍全走 EP0：开 WLAN 时钟、轮询 CMB_CTRL 等 PLL；MAC_SYS_CTRL 先写 3 复位再写 0；写 USB_DMA_CFG(0x238) 打开 bulk 收发 DMA 和接收聚合（之后芯片才会经 EP4 送帧）；MAC 地址写入 0x1008/0x100c；频偏写入 RF R12。`rx-ep=4 data, 5 MCU` 确认端点描述符里选出的两个 IN 端点。

**⑧ `MCU command channel ready tx-ep=8 resp-ep=5 async-prearmed`** —— 第一条 MCU 命令 FUN_SET(Q_SELECT=1)：

```
EP8  bulk OUT 16 B:  08 00 10 50 | 01 00 00 00 01 00 00 00 | 00 00 00 00
                     └ TXINFO 0x50100008：bit30 命令、端口 2、cmd 1、seq 0、长度 8
```

意思是“以后命令的应答从 EP5 送出”，本身不要应答。`async-prearmed`：之后每条要应答的命令，发出前先在 EP5 上挂好接收缓冲（DWC2 ch4）。

**⑨ `MAC/BBP/RF register table initialized (44/59/138 entries)`** —— 全是 EP0 控制写：

| 表 | 每项的控制传输 | 合计 |
| --- | --- | --- |
| MAC 44 项 | 写 2 次 | ≈ 90 |
| BBP 59 项 | 读忙位 + 写 2 次 + 读忙位 ≈ 4 次 | ≈ 240 |
| WCID 地址 / 密钥模式 / WCID 属性 | 516 个寄存器 × 2 | ≈ 1000 |
| RF 138 项 | 读 KICK + 写 2 次 + 读 KICK ≈ 4 次 | ≈ 550 |

BBP 和 RF 寄存器不能直接寻址：要把“寄存器号 + 值 + 忙位”写进间接端口 0x101c（BBP）或 0x0500（RF），再轮询忙位清零，芯片内部才把值送到基带或射频。这是整个探测里 USB 往返最多的一段。

**⑩ `RF calibration complete; bulk endpoints ready`** —— 校准由 MCU 执行，主机发 CALIBRATE（31 号）并等应答，共 8 条：R、TXDCOC、BW×2、LOFT、TXIQ、RXIQ、DPD（中间穿插经 EP0 读写 BBP 158/159 的 RX DC 校准）。以 R 校准为例：

```
EP8  bulk OUT 16 B:  08 00 f1 51 | 01 00 00 00 00 00 00 00 | 00 00 00 00
                     └ 0x51f10008：命令、cmd 31、seq 1、长度 8；载荷 {id = 1 (R), value = 0}
EP5  bulk IN  16 B:  08 00 01 4a | …
                     └ 0x4a010008：bit31–30 = 01 命令应答、seq 1、事件 0 = 完成
```

主机靠 seq 把应答和命令配对。最后写 RX 过滤 0x1400 和 MAC_SYS_CTRL = 0x0c 打开收发——从这一刻起空中的信标开始在接收 DMA 里排队，等着从 EP4 送出。

**⑪ `MCU cmd 12 seq 9 answered after 2 ms; drained 1684 bytes from EP4`** —— 初始换台 `mt7601u_set_channel(1)` 的 RANDOM_WRITE（12 号），写 RF R17–R20：

```
EP8  bulk OUT 40 B:  20 00 c9 50 | 11 00 00 80 99 00 00 00 | 12 00 00 80 … | 00 00 00 00
                     └ 0x50c90020：命令、cmd 12、seq 9、长度 32 = 4 对 {地址, 值}
                       0x80000011 = RF bank 0 的 R17，值 0x99 …
```

seq 是 9，因为前 8 条校准用掉了 1–8。MAC 已经在收，EP4 里排着 1684 B 信标；芯片的接收 DMA 按顺序吐数据，不读走它们 EP5 的应答就出不来。驱动等应答时用 ch3 同步读空 EP4（还没挂接收缓冲，读出的帧丢弃），应答 2 ms 就到了。

**⑫ `EP4 receive uses DWC2 IRQ with 4 buffers`** —— 4 次 `bulk_rx_arm(EP4, 16 KiB)`：在 ch4 上填 HCDMA（总线地址）、HCTSIZ（16384 B = 32 包，DATA0/1）、HCCHAR（addr 3、EP4、IN、bulk、512），打开中断。之后 DWC2 自动反复发 IN 令牌：网卡没数据回 NAK，有数据就送一个以短包结尾的聚合包 → ch4 中断 → `dwc2_irq()` → `mt7601u_rx_irq()` → NAPI → `mt7601u_rx_parse()` 拆帧 → 立即重挂。4 个缓冲轮转，EP4 总有人在收，⑪ 那种拥堵不再出现。

**⑬ `transport and MCU ready; SoftMAC initialization pending`** —— `mt7601u_probe()` 返回，不再有同步 USB 通信。扫描、认证、关联、握手由 `state_work` 推进：发帧走 EP8（802.11 TXINFO + 20 B TXWI），收帧靠 EP4 中断，换信道再发 RANDOM_WRITE / CALIBRATE 并等 EP5。

**小结：探测期间各端点的用量**

| 端点 | 做了什么 | 次数 |
| --- | --- | --- |
| EP0 控制 | 读版本、FCE、启动 MCU、eFuse、寄存器表、BBP/RF 间接访问、RX DC 校准 | 两千次以上 |
| EP8 bulk OUT | 4 块固件、FUN_SET、8 条校准、换台 RANDOM_WRITE | 十几次（4 次大块） |
| EP5 bulk IN | 每条要应答的命令一次 16 B 应答 | 9 次（seq 1–9） |
| EP4 bulk IN | 打开 MAC 接收后信标排队；先同步读空，再交给 4 个异步缓冲 | 持续 |

## 6. 空口：网卡与 AP 之间的报文

### 6a. 一帧怎样从主机到空中

```
EP8 bulk OUT:  TXINFO 4 B | TXWI 20 B | MPDU（802.11 头 24 B + 帧体）| 补齐到 4 B | 00 00 00 00
TXINFO  = 长度 | bit19 802.11 包 | bit24 WIV（置位 = 硬件不加 IV、不加密）
TXWI    = rate_ctl 0（CCK 1 Mbit/s）· ack_ctl 1（要 ACK）· WCID · len_ctl = MPDU 长度
```

FCS（4 B CRC）由芯片发射时附加；对方的 ACK 和重传也由芯片硬件完成，主机看不到。管理帧用 WCID 0xff、置 WIV；关联后的数据帧（包括 EAPOL）用 WCID 1。接收方向：EP4 上每段 = 4 B 长度 + 28 B RXWI + MPDU（已去 FCS）+ 4 B 尾。

本机 SA = `90:de:80:14:95:94`，AP 的 BSSID = `f0:09:0d:cb:b1:14`。帧控制按空中字节顺序写（第 1 字节类型/子类型，第 2 字节 ToDS/FromDS/Protected 等标志）。

### 6b. 报文一览

| 报文（日志） | 方向 | 帧控制 | 帧体要点 |
| --- | --- | --- | --- |
| Beacon（`AP ssid=TP-Link_B114 … channel=8 WPA2`） | AP→ | `80 00` | 时间戳、间隔、能力；IE：SSID(0)、速率(1)、DS 参数(3) = 信道 8、RSN(48) 22 B |
| Authentication（`authentication request sent`） | →AP | `b0 00` | 算法 `00 00`（Open System）、序号 `01 00`、状态 `00 00`；MPDU 30 B |
| Authentication（`Open-System authentication accepted`） | AP→ | `b0 00` | 算法 0、序号 2、状态 0 |
| Association Request（`rsn=22 bytes`） | →AP | `00 00` | 能力、监听间隔 `0a 00`；SSID IE `00 0c "TP-Link_B114"`；速率 IE `01 08 82 84 8b 96 0c 12 18 24`；AP 的 RSN IE 原样附上；MPDU 74 B |
| Association Response（`associated aid=3`） | AP→ | `10 00` | 能力、状态 `00 00`、AID `03 c0`（高两位恒为 1，AID = 3） |
| EAPOL M1（`received WPA2 EAPOL M1 key-info=8a`） | AP→ | `08 02` | 数据帧、FromDS、明文；LLC `aa aa 03 00 00 00 88 8e`；EAPOL `02 03 00 5f`；key-info 0x008a；ANonce |
| EAPOL M2（`sent WPA2 EAPOL M2 replay=0001`） | →AP | `08 01` | ToDS、明文（WIV=1、WCID 1）；key-info 0x010a；SNonce；MIC；key data = RSN IE |
| EAPOL M3（无日志行） | AP→ | `08 02` | key-info 含 Install/ACK/MIC/Secure/加密数据（典型 0x13ca）；key data 用 KEK 包裹：RSN IE + GTK KDE |
| EAPOL M4（`sent WPA2 EAPOL M4`） | →AP | `08 01` | key-info 0x030a；回显 M3 的重放计数器；无 nonce、无 key data；明文 |
| 加密数据 | 双向 | `08 41` / `08 42` | ToDS 或 FromDS + Protected；802.11 头后 8 B CCMP 头，帧尾 8 B MIC |

### 6c. 扫描：从 Beacon 里读出什么

`rx_mgmt()` 只看子类型 8（beacon）和 5（probe response），从固定字段之后逐个解析 IE：0 号 SSID，3 号 DS Parameter Set 给出 AP 实际所在的信道，48 号 RSN。这次 AP 的 RSN IE：

```
30 14 | 01 00 | 00 0f ac 04 | 01 00 00 0f ac 04 | 01 00 00 0f ac 02 | cc cc
  长度   版本     组密码 CCMP     1 个成对密码 CCMP    1 个 AKM：PSK      RSN 能力
```

日志 `group-cipher=4` 就是组密码的类型字节 4（CCMP）。RSN IE 要原样放进关联请求和 M2，AP 逐字节比对，防止降级攻击。在相邻信道也能听到信标，所以命中目标后先切到 DS IE 给出的信道（`tuning to AP channel 8`）再认证。

### 6d. 认证与关联

Open System 认证只是交换两个空的认证帧：本机发序号 1，AP 回序号 2、状态 0。关联请求带能力、监听间隔 10、SSID、速率（`0x82 0x84 0x8b 0x96` 是最高位置 1 的基本速率 1/2/5.5/11 Mbit/s，后四个是 6/9/12/18 Mbit/s 的 OFDM 速率）和 RSN IE。三个地址：A1 = 接收者、A2 = 发送者、A3 = BSSID；STA 和 AP 之间的管理帧里 A1、A3 都是 AP。

### 6e. EAPOL-Key 帧格式

四次握手的报文都是数据帧，帧体 = LLC/SNAP（0x888e）+ EAPOL 头 4 B（版本、类型 3 = Key、长度）+ 95 B 固定部分 + key data：

```
偏移  0   描述符类型 2（RSN）     1-2  key-info              3-4  密钥长度（16）
      5   重放计数器 8 B           13   nonce 32 B
     45   EAPOL-Key IV 16 B        61   RSC 8 B              69   保留 8 B
     77   MIC 16 B                 93   key data 长度         95   key data
```

key-info：bit0–2 描述符版本（2 = HMAC-SHA1 + AES 包裹）、bit3 成对、bit6 Install、bit7 ACK、bit8 MIC、bit9 Secure、bit12 key data 已加密。M1 0x008a = 版本 2 + 成对 + ACK；M2 0x010a = 版本 2 + 成对 + MIC；M4 0x030a 再加 Secure。`rx_eapol()` 用“ACK 置位且 MIC 未置位”认出 M1，用 0x0188 认出 M3。重放计数器：M1 = 1，M2 回显（`replay=0001`），M3 = 2，M4 回显 M3。

### 6f. 密钥推导（空中不传任何密钥）

```
PMK = PBKDF2-HMAC-SHA1(口令, SSID, 4096 轮, 32 B)                    probe 时预先算好
PTK = PRF-512(PMK, "Pairwise key expansion",
              min(AA,SPA) || max(AA,SPA) || min(ANonce,SNonce) || max(ANonce,SNonce))
    = KCK[0..15] | KEK[16..31] | TK[32..47] | ...                  wpa_derive_ptk()
MIC = HMAC-SHA1(KCK, MIC 字段清零后的整个 EAPOL 帧) 的前 16 B        wpa_eapol_mic()
GTK = AES-Key-Unwrap(KEK, M3 的 key data) 中的 GTK KDE               wpa_aes_unwrap()
```

收到 M1 时本机已有 ANonce 和 SNonce，就能算出 PTK，M2 才能带上 MIC；AP 用同样的公式得到同一个 PTK，验 MIC 通过即证明双方口令一致。M3 解包后是 AP 的 RSN IE 加 GTK KDE：`dd 16 00 0f ac 01 | 01 00 | GTK 16 B`，`01` 的低 2 位是 GTK 序号 1。

### 6g. 装密钥（M4 明文发出之后）

```
0x8000 + 32×1 = 0x8020   TK 16 B                    WCID 1（AP）的成对密钥
0xa000 +  8×1 = 0xa008   01 00 00 20 00 00 00 00     IV 初值：PN = 1，ExtIV 位，key id 0
0xa800 +  4×1 = 0xa804   (4 << 1) | 1 = 9           属性：CCMP、成对
0xac00 + 32×1 = 0xac20   GTK 16 B                    BSS 0 的共享密钥槽 1
0xb000                   4 << (4×1) = 0x40          槽 1 的密码类型：CCMP
```

日志 `attr=11009 skey-mode=11049` 来自先读后改的旧代码（读回的值混入了上一次写入的内容）；现在两处都直接写 0x9 和 0x40。必须先发 M4 再装密钥：认证者收到 M4 后才装密钥，加密的 M4 它解不开，只会重发 M3。

### 6h. 加密数据帧

`mt7601u_net_xmit()` 发出的数据帧帧控制 `08 41`（ToDS + Protected），TXINFO 清 WIV：芯片按 WCID 1 的 IV 表在 802.11 头后插入 8 B CCMP 头（PN 自动递增），用 TK 加密帧体并追加 8 B MIC。接收时单播帧（`08 42`）用 PTK 解、组播/广播用槽 1 的 GTK 解；RXWI DECRYPT 位表示已解密，PN_LEN 非零时 CCMP 头仍在帧里，所以 `rx_data()` 从第 32 字节找 LLC 头。

### 6i. 状态机与调用路径

```
dwc2_irq() ── ch4 完成 ──→ mt7601u_rx_irq() → napi_schedule()
   mt7601u_napi_poll() → mt7601u_service(1, 0)
      bulk_rx_complete(EP4) → mt7601u_rx_parse() → rx_mgmt() / rx_data() → rx_eapol()
      bulk_rx_arm(EP4)；交付接收队列 → net_rx_dev()

state_work → mt7601u_state_worker() → mt7601u_service(0, 1)
   SCAN          每 50 tick：锁外 mt7601u_scan_switch() → mt7601u_set_channel(next)
   AUTH_PENDING  当前信道 ≠ AP 信道 → 先切过去；否则 mt7601u_send_auth()
   ASSOC_PENDING mt7601u_send_assoc()
   ASSOCIATED    500 tick 等 M1 的看门狗

发送：netdev_xmit → mt7601u_net_xmit() → mt7601u_send_llc(encrypted=1)
      → mt7601u_tx_raw(WCID 1) → dwc2_usb_bulk(EP8)
```

认证、关联各最多重试 3 次，响应超时 100 tick；收到 AP 的解除认证/解除关联（如空闲后的 `reason=6`）就清握手状态、回到认证阶段重连。

## 7. 调试实录：从“校准失败”到“DHCP 成功”

| 现象（日志） | 原因 | 修改 |
| --- | --- | --- |
| `channel switch to 2 failed`，0x0500 一直读到 `f8 42 63 bd` 并无限刷屏 | 直接写 `RF_CSR_CFG` 和运行中的 MCU 抢间接端口；换台在自旋锁内、失败无限重试 | 频率表改用 MCU `RANDOM_WRITE`；换台挪到锁外，失败退避，8 次后停止扫描，首次失败打印诊断 |
| `calibration 4 failed`（LOFT 无应答） | 校准顺序不全：少了 RXDC 和 BW 滤波 | 按 Linux `mt7601u_init_cal()` 补全顺序 |
| 第三条 MCU 命令总是收不到应答 | 芯片 RX DMA 按序吐数据：EP4 里没人读的帧把 EP5 的应答堵在后面（Linux 的 EP4 URB 一直挂着） | 等应答时交替清空 EP4；证据：`answered after 11 polls; drained 148 bytes` |
| 改成 EP5 异步预挂后 `no response after 1500 ms` | probe 在 `main()` 里执行，中断未开，`dwc2_irq_pending` 永远不置位；且 EP4 占满 4 个槽 | `bulk_rx_complete()` 直接轮询 HCINT(4)；槽位 4→5；ch4 轮转调度 |
| 打印刷屏数分钟 | 2 ms 轮询 + 每包 3 行 `usb-xfer` 跟踪，串口打印比轮询还慢 | 空轮询不打印；`USB_XFER_TRACE` 置 0 |
| 认证前两次超时 | 在相邻信道听到 AP 信标就发认证 | 认证前切到 AP 的 DS 信道 |
| M4 重发 3 次 | M4 带 Protected 位，且先装密钥后发 M4，AP 解不开 | 先明文发 M4，再装密钥（IEEE 802.11 12.7.6.5） |
| DHCP 无 Offer：`rx drop … ICV`（组播帧） | WCID 属性表、共享密钥模式、WCID 地址表从未初始化，上电随机值让硬件取错密钥 | 按 Linux `init_wcid_mem/init_key_mem/init_wcid_attr_mem` 初始化，属性与模式直接写入 |
| 解密后的帧被静默丢弃 | PN_LEN≠0 时硬件保留 8 B CCMP 头，被当成 LLC 头 | `rx_data()` 跳过 CCMP 头（日志 `hdr=32`） |
| 聚合包里多帧只交付一帧 | 单槽 `net_rx` | 8 帧环形队列，锁内拷贝、锁外交付 |
| 空闲后 `reason=6` | AP 清掉了长时间无流量的客户端，驱动不知道 | 处理 deauth/disassoc，自动重连 |

## 8. 现状与待改进

- **没有热插拔**：集线器端口只在启动时扫描一次，找到 MT7601U 就停下；`usb_child` 是单个静态设备。
- **Wi-Fi 参数写在驱动里**：SSID 和口令写死在 `mt7601u.c`；`/etc/wifi.conf` 经 `wifi_connect()` 只交给板载芯片的 `brcmfmac_connect()`（期间还会 `mt7601u_pause(1)`）。
- **没有保活**：空闲后会被 AP 踢掉，重连后需要重新 `dhcp wlan1`；应每 30–60 s 发一个 null-data 帧。
- **只用一个 bulk OUT**：固件、MCU 命令和数据帧都走 EP8，Linux 把数据分到 EP4–EP7 的 WMM 队列。
- **寄存器读偶尔拿到旧值**：`keys installed` 曾读回 `0x11009`（上一次写入的值），疑为控制 IN 的 DMA 缓冲问题，待查。
- **调试输出**：`rx data/rx drop/tx data/keys installed/dhcp: rx` 等诊断在稳定后应删除或放到开关后面。
- **版本字符串不一致**：probe 打印 `driver WPA2-v4`，找到目标时打印 `driver=WPA2-v3`。
